# 지표 판단 — 사람이 쓰는 층 (2층)

> 1층(`fields.md`)은 **기계가 코드에서 뽑는다** — 이름·DB표현식·수집기·주기·채움률.
> 이 파일은 기계가 못 뽑는 것을 쓴다: **이 값이 사실 무엇인가**, **믿을 만한가**, **점수에 써도 되나**.
>
> ⚠️ 이 파일은 사람이 쓰므로 **낡는다**. 각 항목에 `확인일`을 적고, 그 날짜가 오래됐으면 다시 실측한다.
> 채울 수 없는 칸은 **"미확인"으로 남긴다** — 그럴듯하게 채우면 백서가 거짓말을 시작한다.

## 시간 성격 — 점수에 쓸 수 있는지 가르는 기준

아파트는 **오래 살 집**이다. 그래서 "오늘 어땠나"가 아니라 "이 단지의 성질"로 채점해야 한다.

- 🔴 **날/주 단위로 바뀜** → 점수에 쓰면 안 된다
- 🟡 **월/분기** → 쓸 수 있으나 "언제 기준"인지 화면에 밝힌다
- 🟢 **년 단위 이하 또는 고정** → 안전

## 🔴 위험 — 세션559 실측으로 확인, 처리 중

### `unsoldRate` / `unsold` — "미분양"이 미분양이 아니었다

| | |
|---|---|
| 화면 이름 | "미분양 세대", "미분양률" |
| **실제 내용물(옛)** | **오늘 네이버에 올라온 매매 매물 수** ÷ 총세대수 |
| **실제 내용물(새)** | 청약홈 단지별 실측 > KOSIS 시군구 미분양 **비례배분 추정치** |
| 점수 비중 | 안전 14% |
| 확인일 | 2026-09-22 |

**실측 근거**: 1,989곳 중 **1,157곳(58%)**의 `unsold` 가 `naver_sell_count` 와 **완전히 동일**.
**81곳**은 미분양이 총세대수를 넘었다(세종더샵예미지 L4블록 = 1세대인데 18, 미분양률 최대 **11,800%**(익산 제일풍경채 어바니티 = 1세대에 118)).

**왜 생겼나**: `sync-naver-complex.mjs` 에 "매매 매물 수를 미분양 근사치로 사용"이라 적혀 있었다.
데이터가 부족하니 매물 수로라도 채우자는 의도였는데, 그 근사가 틀렸고 점수까지 흘러갔다.
`collect-unsold-kosis.mjs` 는 "우선순위: 청약홈 > 네이버 > KOSIS" 로 **공식 통계를 매물보다 아래**에 뒀다.

**이미 있던 방어의 한계**(⚠️ 세션559 말미 정정): `fieldMeta.ts:60-64` 의 가드는 **`units`(총세대수) 필드**에 달려 있어
**총세대수 쪽을** '정보 없음'으로 가린다. `unsold`(미분양, :67-72)에는 가드가 없다 — 즉 그 81곳은 화면에
**"총세대수: 정보 없음 / 미분양 18세대"** 로 나왔다. 내가 처음 "미분양이 가려진다"고 적은 것은 틀렸고, 실제는 더 나빴다.
어느 쪽이든
**화면만 가렸고 점수는 그 값을 그대로 썼다** — 손님 눈엔 안 보이는데 점수는 깎이는 상태였다.

**처리**: 네이버 기록 제거 + KOSIS 우선순위 복원(`shouldSkipKosisFill`) + 오염 81곳 정리
스크립트(`cleanup-listing-based-unsold.mjs`).

⚠️ **남은 한계**: `units <= 1` 인 19곳은 비례배분 분모가 없어 KOSIS 로도 못 채운다 → 지운 뒤 **"모름"**.
그리고 **KOSIS 값은 단지별 실측이 아니라 구 단위 통계를 세대수 비례로 나눈 추정치**다.
같은 구의 단지는 비슷한 값을 받는다 — 화면에 그 한계를 밝혀야 한다(미구현).

### `naverSellCount` 기반 매물 과잉 벌점 — 제거됨

| | |
|---|---|
| 옛 동작 | 매물 > 50건이면 위험 +5, > 30건이면 +2 |
| 왜 틀렸나 | ① 매물은 **매일 새벽 통째로 갈린다** ② 절대 개수라 **단지 규모를 무시**(실측 최대 566건) |
| 실측 | 경계 근처(25~35 · 45~55건)에 **325곳** — 매물 하나에 점수가 붙었다 떨어졌다 |
| 확인일 | 2026-09-22 |

**처리**: 삭제. 규모 보정(매물÷세대수)을 하면 `unsoldRate` 와 같은 값이라 **중복 감점**이므로 되살리지 않는다.
매물 수 자체는 `naverSellCount` 로 화면에 남긴다 — **"오늘 나와 있는 매물 수"라는 정직한 이름**이라 쓸모가 있다.

### `airQuality` — "오늘 하루" 미세먼지로 채점 → **3년 평균으로 교체 완료(세션560)**

| | |
|---|---|
| 화면 이름 | "대기질 / 3년평균 PM2.5: 17.2 / 오늘: 보통" |
| **실제 내용물** | **채점** = 에어코리아 최종확정 3년 평균(2022~2024) · **"오늘"** = 실시간 통합지수(참고용) |
| 점수 비중 | 입지의 환경 축(환경이 입지의 10%, 그 안에서 넷 중 하나) |
| 확인일 | 2026-09-22 (세션560에 교체) |

**실측 근거**: 오늘값은 3,068단지를 **"보통"(1,581) / "좋음"(1,383) 두 갈래**로만 갈랐다(서로 다른 값 29종).
3년 평균은 **10.25~26.03**(단지에 붙은 값 기준)에 고르게 퍼진다(**325종, 11배**).
⚠️ 모수 주의 — 측정소 651곳 표 자체의 최대는 **32.99** 지만, 그 측정소를 쓰는 단지가 없다.
경계 설계("최대 26 이라 셋째 칸이 빈다")의 근거는 **단지 기준 26.03** 이다(세션560 할루시네이션 감사 정정).

**후속(세션561, 2026-09-23) — PM10·O3 도 같은 병이 있었다**: 세션560이 PM2.5 만 3년 평균으로 바꾸고
`annual.pm10`·`annual.o3` 도 함께 먹였는데 **그 두 등급표는 옛 실시간 척도 그대로**였다.
`airSc = pm25*0.4 + pm10*0.35 + o3*0.25` 이라 **점수의 60%** 가 맞지 않는 잣대였다.

| 축 | 옛 경계 | 3년 평균 실측 | 옛 상태 | 새 경계(사장님 확정) |
|---|---|---|---|---|
| PM10 | 30/80/150 | min 21.72 · 중앙 33 · **max 60.49** | `{max:150}` 도달 불가 → **2칸** | **30 / 36** (11.5/47.2/41.3%) |
| O3 | 0.03/0.09 | min 0.01626 · 중앙 0.03215 · **max 0.05056** | `>0.09` 사문화 → **2칸** | **0.030 / 0.035** (37.7/54.1/8.3%) |

⚠️ **PM10 국가 대기환경기준(연평균 50)은 쓸 수 없다** — 실측 최대가 60.49 라 단지 **100%** 가
"좋음" 한 칸에 몰려 순위를 전혀 못 가른다(실측 확인). O3 는 **연평균 기준이 아예 없다**
(8시간 0.06ppm 이라 3년 평균과 단위가 다름). 그래서 둘 다 실측 분포로 정했다.

중립값(자료 없음)도 12 → **14**(가운데 칸)로 맞췄다 — "측정소가 우리 표에 없다"는 **우리 자료 사정**이
그대로 감점이 되던 것을 없앴다. 반영 결과 단지 **2,457곳 중 193곳**의 입지 점수가 움직였다(최대 ±1점).

⚠️ **손님 문구도 함께 고쳤다**: 옛 설명은 `" /PM10"`·`" /O3"` 라는 **빈 이름표**라 경계 숫자가
없었다. 이제 등급표에서 **유도**되므로 경계를 옮기면 문구가 따라온다([[score-meaning-and-wording-are-a-pair]]).
지역 순위도 뒤집힌다 —
오늘값 1위 강원(9.4)·꼴찌 전북(19.7) vs 3년평균 1위 **제주(13.8)**·꼴찌 **충남(20.7)**.

**⚠️ 화면 글자의 출처가 점수표가 아니다**: "대기: 보통"은 `air_quality.grade` 이고 그건
에어코리아 **실시간 통합지수(khaiGrade)** 다. 점수만 3년 평균으로 바꾸면 **점수와 글자가 서로 다른 말**을 한다.

**처리**: 3년 평균(에어코리아 최종확정 측정자료 2022~2024)으로 교체 — **완료(세션560)**.

세션559가 표(`air_station_annual`)까지 만들었으나 **그 표를 읽는 코드가 0건**이라 값이 점수에 닿지
않는 중간 상태였다(실측: `grep -rn air_station_annual` → 쓰는 곳·정의뿐). 세션560이 전달 통로
(`air-annual-attach.mjs`)를 만들고 채점·문구를 함께 옮겼다.

- **경계**(사장님 확정 2026-09-22): 3칸 `15 / 19` → 20 / 14 / 8점. 첫 경계 15 는 **국가 대기환경기준**.
  옛 경계(15/25/50)는 오늘값 기준이라 3년 평균에서는 **단지 91.3% 가 한 칸에 뭉쳤다**(변별력 없음).
  새 경계 실측 분포: 20점 250곳(8.4%) / 14점 1,611곳(53.8%) / 8점 1,131곳(37.8%).
  ⚠️ **분모는 전부 2,992곳**(3년 평균이 붙은 단지). 초판은 91.6% 로 적었는데 그건 분자만 76곳
  폴백을 포함하고 분모를 3,068 로 바꿔야 나오는 값이었다 — 한 문단 안에서 모수가 갈렸다
  (세션560 할루시네이션 감사 정정).
- **문구**: `AIR_ANNUAL_LABELS`·`airAnnualBand()`·`AIR_ANNUAL_LEGEND` 로 **경계에서 파생**시켜,
  경계를 옮기면 문구가 따라오게 했다(선례 = `LIQUIDITY_LABELS`). 실시간 값은 "오늘:" 로 자리 이동.
- **폴백**: 3년 평균이 없는 **76곳**(측정소 13종, 표본이 얇아 걸러진 것)은 `AIR_QUALITY_DEFAULT = 14`
  = **가운데 칸**. 옛 값 12 는 새 경계에서 가운데보다 낮아 "우리 자료 사정"이 감점으로 변했다.
- ⚠️ **조용한 유실 통로를 같이 막았다**: 매일 도는 `collect-air-quality.mjs` 가 `air_quality` 를
  **통째로 교체**해(`update({ air_quality: aq })`) 붙여 둔 `annual` 이 다음 날 새벽에 날아갈 상태였다.
  기존 `annual` 을 보존하도록 고쳤다 — 안 고쳤으면 에러도 경보도 없이 전 단지가 폴백으로 떨어진다.

## ⚠️ 검사관이 잡은 것 (세션559 말미 적대검증 3명)

### 🔴 "1,090곳은 KOSIS 가 다음 회차에 덮어쓴다" — **사실이 아니었다**

PR #547 본문과 정리 도구 주석에 그렇게 적었는데, 적대검증이 `shouldSkipKosisFill` 을
실제로 1,090곳에 돌려 보니 **1,090곳 전부 건너뛰었다(100%)**.

원인: 매물 유래 값은 **대부분 세대수 이내**라 `unsold <= units` 조건에 걸려
"유효한 기존 값"으로 분류됐다. 즉 내가 만든 규칙이 **cleanup 이 이미 지운 81곳만** 대상으로 했고,
남은 1,090곳에는 **아무 경로도 닿지 않았다.**

**그중 196곳이 미분양률 15% 초과로 안전 점수를 깎는 중이었다**
(두산위브 트리니뷰 구명역: **31세대인데 미분양 30**(=매물 30건) = 96.8%).

→ 처방: `unsold === naver_sell_count` 면 매물 유래로 보고 덮어쓴다. 실측 **1,083/1,090** 해소.
  잔여 7곳은 **세종**(구·군이 없어 `gu=null`, 비례배분 분모 없음) — 별개 구조 문제.

⚠️ **가장 나쁜 건 코드가 아니라 글이었다.** "자동 해소된다"고 적어 다음 사람이 확인 안 하게 만들었다.

### 🔴 좀비 테스트 — 어느 방향으로도 실패하지 않는 가드

`engine.test.js` 의 `"scoreRisk — naverSellCount 매물과잉 페널티"` 가 `toBeLessThanOrEqual` 이라
**페널티가 있든 없든 통과**했다. 기능은 세션559에 삭제됐는데 이름만 남아 다음 사람이
"페널티가 아직 있구나" 로 오독한다. 세션555의 "깃발 stub 테스트"와 같은 종류.
→ `toBe(base)` 로 **"영향이 없음"을 못 박는** 가드로 교체(페널티를 되살리면 red).

### 🔴 완판 실측 91곳을 구 추정치가 덮어씀

`unsold === 0`("다 팔렸다")을 "값 없음"으로 보고 덮어쓰고 있었다 — 이 수집기가 내세운 원칙
(**단지별 실측 > 구 단위 비례배분**)과 정면으로 어긋난다. → `0` 은 존중하도록 정정(사장님 결정).

### 🟡 `hideNoUnsold` — 손님 목록의 모집단이 바뀐다 (미해결)

`src/App.tsx:93` 이 이 필터를 **기본 켜짐**으로 두고, `useDataPipeline.ts:283,378` 이
`unsold > 0` 인 단지만 목록에 남긴다. **미분양 값을 바꾸면 목록에 뜨는 단지 자체가 달라진다.**

실측: 지금 **2,535곳**이 목록에 뜨고, 다음 KOSIS 회차가 채울 후보가 **398곳** →
최대 **2,933곳**으로 늘 수 있다(+16%). **반영 전에 재 둔 값이다 — 반영 후엔 전을 못 잰다.**

## 🟢 확인했으나 문제 없던 것 — 과장했다가 정정

### `nearbyMedian` / `jeonseRate` / `psr` — 호가 폴백은 거의 발동하지 않는다

조사 보고는 "실거래 3건 미만이면 네이버 **호가**로 폴백하므로 가격 점수의 75%가 위험"이라 했고
나도 그대로 보고했다. **틀렸다.**

**실측**: 폴백 판정은 **구 단위 12개월 거래 3건 미만**인데, 구 단위 거래는 **중앙값 1,672건**이다.
조건에 걸리는 곳은 3,068곳 중 **1곳**뿐이다.

**교훈**: 폴백 조건의 **모수가 무엇인지**(단지별? 구별?) 확인하지 않고 옮겨 적었다.
남의 조사 보고는 **규모를 재고 나서** 인용한다.

⚠️ 다만 **`medianSource`(실거래인지 호가인지)를 계산하고 버린다** — DB 에 기록하지 않아
그 1곳이 어디인지, 앞으로 늘어나는지 알 방법이 없다. 기록하는 편이 낫다(미구현).

## 🟡 주의 — 세션561 실측으로 확인

### `coordShared` — 좌표를 남의 단지와 공유하는 행 (신설)

| | |
|---|---|
| 화면 이름 | (값 자체는 미표시 — 교통 카드 경고로만 나타난다) |
| **실제 내용물** | 지오코딩이 단지를 못 찾아 **구청 같은 대표 장소 좌표**로 떨어진 행 |
| 점수 비중 | 직접 0 — 다만 **이 좌표로 재는 것이 전부** 틀린다(교통·학군·인프라·대기질 측정소) |
| 확인일 | 2026-09-23 |

**실측**: **56곳**(그중 손님 화면 노출 **40곳** = 2,457 중 1.6%). 채움률 1.6%.

**판정 주체는 이 필드가 아니다** — `fix-placeholder-addresses.mjs` 의 `findTruePlaceholders`
(카카오 POI·청약홈 주소·네이버 단지 **세 출처가 모두 실패**한 행 = `tier === "none"`)가 정한다.

⚠️ **"좌표가 같다"로 세면 안 된다.** 소수 5자리까지 같은 좌표를 공유하는 단지는 891곳이지만,
그중 대부분은 **같은 부지의 회차 분리**라 정상이다. 세션561에 이 잣대로 세었다가 891곳으로
15배 부풀렸다(세션560도 29→36→95 로 세 번 출렁였다). 진짜 신호는 **"그 좌표가 그 단지에서 먼가"**
이고, 그건 위 도구가 이미 푼 문제다([[same-coordinate-is-not-a-defect]]).

**왜 고치지 않고 표시만 하나**: 남은 것들은 **아직 준공 전이라 지도에 없어서** 세 출처가 전부
정답을 못 찾는다(같은 날 1,860곳 조사 → 정정 대상 **0곳**). 추측으로 옮기면 멀쩡한 좌표를 망친다
(형제 행 좌표를 쓰려다 `금강펜테리움 6차`↔`7차` 같은 별개 단지를 묶는 규칙이 나와 폐기).

**손님에게는** 상세 화면 교통 카드에 한 줄 경고로 나타난다(세션561) — "아직 준공 전이라 위치가
정확하지 않을 수 있습니다". 40곳 전부 교통 필드가 있어 카드가 안 떠서 경고를 놓치는 곳은 **0곳**.


### `avgMaintenanceCost` — 매일 도는 네이버가 월 1회 공식 API 값을 덮어쓴다 (확인됨)

| | |
|---|---|
| 화면 이름 | 평균 관리비 (만원) |
| 쓰는 수집기 | `collect-maintenance.mjs`(공식 API, **월 1회**) · `sync-naver-complex.mjs`(네이버, **매일**) |
| 점수 비중 | 혜택(Benefit) |
| 확인일 | 2026-09-23 |

**실측 근거**: `avg_maintenance_cost` 보유 **2,466곳** 중, 공식 API 항목(`maint_heat`/`maint_elec`/`maint_water`)도
함께 가진 곳이 **949곳**이다. 이 949곳이 덮어쓰기에 노출돼 있다.

**코드 근거**: `sync-naver-complex.mjs:838-839` 가 **조건 없이** 덮어쓴다 —
`if (agg.costs.length > 0) row.avg_maintenance_cost = …`. 그 값이 공식 통계에서 온 것인지
보지 않는다. 반면 `collect-maintenance.mjs` 는 월 1회만 돈다. 그래서 **매일이 월 1회를 이긴다.**

⚠️ **아직 고치지 않았다.** 무엇이 더 옳은 값인지(공식 API 고시 관리비 vs 네이버 매물의 실제 관리비)가
먼저 정해져야 한다 — 둘은 **다른 것을 재는 값**일 수 있다. 세션559의 `unsold` 와 같은 결:
"이름이 내용물을 보장하지 않는다". 사장님 판단이 필요한 자리.

### `apartments_flat` 2,457행 vs `apartments` 3,068행 — **의도된 중복 제거였다**

**611곳이 화면에 안 나가는 이유가 확인됐다: 데이터 유실이 아니라 VIEW 의 중복 제거다.**

**실측 근거**(2026-09-23): 이름(끝 괄호 제거)·지역·시군구·동으로 묶으면 **중복 묶음 264개**에
**875곳**이 들어 있고, 각 묶음에서 대표 1곳만 남으므로 탈락 수는 `875 − 264 = ` **611곳** —
빠진 수와 **정확히 일치**한다.

**실물 예시**: `화곡 더리브 스카이 주상복합아파트` 는 (임의공급 2차)~(5차) 등으로 **16곳**이
등록돼 있다. `신림스카이아파트` 14곳, `현대 프라힐스 소사역 더프라임` 15곳도 같은 꼴이다.
전부 **같은 단지의 회차 분리**라, 손님 목록에 16번 나오지 않게 하나로 묶는 것이 맞다.

⚠️ 다만 대표를 고르는 규칙(`ORDER BY (name LIKE '%(오)%') ASC, id DESC`)이 **어느 회차를
남기는지**는 별도 판단거리다 — 회차마다 분양가·세대수가 다르면 대표값도 달라진다(미확인).
