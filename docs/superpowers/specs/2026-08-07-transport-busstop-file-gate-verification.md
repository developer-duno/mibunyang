## 게이트 1 — 반경 정밀 역산

### 방법

PR #335 설계문서의 3표본 추정(450~500m)을 N≥20으로 재확정하기 위해:

1. Supabase `transport` 테이블에서 `bus_routes` 1~14(15 캡 제외 — 캡에 걸리면 최대거리가 잘려
   반경 추정이 왜곡된다)인 apartment 를 지역별로 균등 추출.
2. **⚠️ 첫 시도(33건, DB `bus_routes` 8~14 위주 선택)에서 24/33이 실시간 캡(15)에 걸림을 발견** —
   `bus_routes`(DB)는 이름 dedup **후** 값이라, DB 값이 8~14 여도 dedup **전** 원시 응답이 이미
   15 캡에 닿아 있을 수 있다는 걸 실측으로 알게 됐다(선택 전략 오류를 실측 중 발견·정정).
3. 2차 시도(34건, DB `bus_routes` 1~6 위주로 전략 수정)로 보강 — 캡을 피할 확률이 높은 표본을
   추가 확보.
4. 각 표본 좌표로 TAGO `getCrdntPrxmtSttnList` 를 실제 호출(300ms+ 간격 — 실측 350ms), 반환된
   정류장 좌표로 haversine 거리 계산, 표본별 **최대거리** 산출.
5. 캡(15)에 걸린 표본과 0건 응답은 통계에서 제외(그 사실을 기록).

**⚠️ 키 조달 문제**: `.env.local` 에 `TAGO_KEY` 가 없었다(`.claude/API_REGISTRY.md` 에 등재된
정상적인 환경변수명은 맞으나, 이 작업 환경의 로컬 파일엔 값이 없음 — GitHub Secrets 에는 있을
수 있으나 이 세션에서 확인 불가). data.go.kr 는 "포털 1계정의 인증키를 여러 API 가 공유"하는
구조라는 문서(API_REGISTRY.md §1)에 따라, **1회 검증 호출**로 `MOLIT_KEY` 가 같은
`BusSttnInfoInqireService` 엔드포인트에 통하는지 확인했다 — **HTTP 200·`resultCode:"00"` 정상
응답 확인**. 이후 게이트1·2의 모든 라이브 호출은 `MOLIT_KEY` 로 진행했다. **이건 이 세션의
임시 조치일 뿐, 실제 구현 코드는 여전히 `TAGO_KEY` 를 읽어야 한다** — 로컬 `.env.local` 에
`TAGO_KEY` 동기화가 필요하다(👤 사장님 몫, §6).

**총 호출 수**: 67회(중복좌표 제거 후) — 애초 목표(60회 이내)를 7회 초과했다. 1차 표본 선택
전략이 편향(캡에 몰림)돼 2차 보강이 필요했던 게 이유다. 미리 낮은 DB값 위주로 뽑았으면
불필요했을 초과라 정직하게 남긴다.

## 게이트 2 — 오프라인 재현 검증

### 사전 선언한 합격 기준 (결과를 보기 전 확정)

1. **±1 이내 일치율 ≥ 90%**
2. **15개(만점) 버킷 비율 ≤ 2%** (DB 기준 0%에 최대한 가까워야 변별력 유지 — PR #335 §2.4.2)
3. **버킷별(0·1~4·5~9·10~14·15) 절대 비율차 합 ≤ 15%p**

### 방법

1. `atchFileId` 를 **매번 resolve** 하는 흐름으로 파일을 새로 받았다(하드코딩 금지 지시 준수) —
   `POST /tcs/dss/selectFileDataDownload.do` → `FILE_000000003558143` 확인(코디네이터 독립
   재현치와 일치) → `GET /cmm/cmm/fileDownload.do?...` → 20,735,435 bytes.
2. **⚠️ 정식 CSV 파서(`csv-parse`, RFC4180 대응 MIT 라이브러리)로 재파싱해 행수 불일치를 해소했다**
   — PR #335 §13 의 "미확정 사항"(메타 206,022 vs 나이브 파싱 226,759)이 남아 있었는데, 정식
   파서로는 **227,065행**(전부 9컬럼 정상 구조, 깨진 행 0건)이 나온다. 나이브 `split(/\r?\n/)` 값
   (227,066/226,759)과는 거의 일치하므로 **줄바꿈 포함 필드 문제가 아니라, 포털 메타데이터
   (`atchFileCo:"206022"`) 자체가 낡은 값**이라는 결론이다(이 파일이 stdrDe=2025-10-31 로 갱신될
   때 메타 카운터가 안 따라온 것으로 추정 — 확정은 아니고 포털 쪽 사정).
3. Supabase `transport` 의 `bus_routes IS NOT NULL` 전체(**2,137건**, PostgREST 페이지네이션으로
   전량 확보)를 검증 표본으로 삼았다 — 지시한 "200건 이상"보다 훨씬 크게, **전수**로 검증했다.
   DB 분포는 PR #335 §2.4.2 표와 정확히 일치(0개 583·1~4개 336·5~9개 874·10~14개 344·15개 0).
4. 그리드 인덱스(0.01도 셀, PR #335 §2.7.2 답습) + haversine 로 반경 필터.
5. **13개 조합**을 시도(반경 {450,500,550} × dedup {이름완전일치, 좌표근접30/50/60m, 이름부분일치
   +좌표근접 OR-매칭, 도시코드 필터} 조합).

### 근본 원인 진단 (실측 사례)

**정류장명 중복 실측**: 전체 227,060행 중 **66,989개 정류장명이 2회 이상** 등장하며, 여기
연관된 행이 **193,486개(전체의 85.2%)**. 완전 동일 좌표(소수 6자리)로도 3,987 그룹·8,053행이
중복. **정류장 대다수가 파일에 여러 행으로 흩어져 있다는 뜻.**

세 지역 실측 사례(반경 500m 이내, dedup 전 원시 행):

1. **인천 계양 하늘채 파크포레**(DB=2): 원시 8행 중 **"청소년수련관.어린이과학관"류가 4행**
   (`GGB167000307`·`ICB167000307`·`GGB167000308`·`ICB167000308` — 경기/인천 두 체계가 각각
   등록, 좌표차 10m 이내), **"박촌역"류도 4행**(같은 패턴). → dedup 해도 최선이 4개인데 DB는 2.
2. **서울 양재리본타워2단지 장기전세**(DB=2): 원시 27행. "더케이호텔후문"(SEB/GGB 체계로 3행),
   "잔디마을"(4행), "하이브랜드"류(6행), "양재IC(미정차)"류(6행) 등 **반경 내 소수의 실제 지점을
   10개+ 행이 중복 서술.**
3. **울산 문수로 푸르지오 어반피스**(DB=1): 원시 28행+(20행까지만 확인). "산업은행앞"(2행),
   "농업인회관"(2행), "신정고등학교"류(4행 — YSB/USB 두 체계 혼재)처럼 **같은 도시 내에서도**
   중복이 나타난다(§도시코드 필터가 안 통한 이유 — 문제가 도시경계 넘나드는 것만이 아니다).

**도시코드 필터가 오히려 악화시킨 이유**: 사례 1·2 처럼 경계지역의 이중등록(GGB/ICB, SEB/GGB)
뿐 아니라, 사례 3 처럼 **같은 도시 안에서도** 이름 변형·재수집 주기 차이로 중복이 발생한다 —
"최근접 정류장의 도시코드만 남기기" 전략은 경계 케이스만 해결하고, 훨씬 큰 비중을 차지하는
동일도시 내 중복은 그대로 두면서 오히려 정상 이웃 지점(다른 도시코드 소속)까지 걸러내
과소평가를 유발했다(15버킷비율이 40~61%로 더 커짐 — 반경 내 후보가 줄어드니 dedup 안 해도
자연히 cap 을 더 자주 못 넘기게 됐을 뿐, 진짜 개수 추정은 더 나빠짐).

### 조사했으나 기각한 대안 — "전국버스정류소표준데이터"(#15096280)

정류장 개수가 정제된 별도 데이터셋이 있는지 확인했다. `data.go.kr/data/15096280/standard.do`
페이지를 열어보니 **"OpenAPI 활용신청" 버튼이 이미 쓰고 있는 `BusSttnInfoInqireService`
(publicDataPk 15098534)로 연결된다** — "표준데이터"는 별도의 정제된 CSV 가 아니라 국가 데이터
표준 스키마 카탈로그 항목이었고, 실체는 우리가 이미 호출 중인 실시간 API 와 같은 계열이다.
**이 경로로는 중복 문제가 해소되지 않는다** — 더 조사할 다른 후보(예: 시군구별 개별 표준
데이터셋을 100+개 따로 받아 합치는 방법)는 있을 수 있으나, 이번 게이트 범위를 크게 벗어난다고
판단해 여기서 멈췄다.

## 결론 및 권고

**PR #335 §2.8 이 요구한 재현 목표("점수 변화 ≈ 0")를 이 파일 데이터셋으로는 달성할 수 없다.**
반경은 확정했지만(게이트 1, 신뢰도 높음), 파일 자체의 다중 등록 문제가 어떤 기하학적 dedup
휴리스틱보다 크고 불규칙해서(경계지역·동일도시 내부·연도별 재수집이 뒤섞임) **13개 조합 모두
큰 폭으로 실패**했다.

**PR #335 §8 이 이미 마련해둔 후퇴 경로를 그대로 따른다**: "검증에서 재현이 어렵다고 판명되면
A(로컬 이전)로 후퇴한다" — 설계문서 §3 에 A안 전체 세부설계(스케줄·감사영향·롤백)가 이미 완성돼
있다. **이 문서는 그 판단의 근거이지, 다음 행동을 자동으로 정하지 않는다** — §1 의 진단
재검토(같은 게이트웨이의 collect-maintenance 는 정상 수집)가 여전히 유효하므로, A안이 실제로
문제를 해결할지도 불확실하다. **사장님 판단이 필요한 지점**이다(아래 §6).

## 향후 재도전 조건 (참고, 지금 착수 안 함)

이 파일 데이터셋으로 B안을 다시 시도하려면 다음 중 하나가 필요하다:

1. **더 정교한 중복해소 알고리즘** — 예: 정류장 ID 접두사(도시코드 2자)·수집일자·모바일단축번호
   조합으로 "같은 물리적 정류장"을 판별하는 규칙을 국토부에 문의하거나 공식 문서에서 찾기.
2. **다른 데이터 소스** — 시군구별 개별 표준데이터셋을 낱개로 받아 정제하는 방법(전수 100+ 지자체
   조사 필요, 매우 큰 작업).
3. **TAGO 실시간 API 자체의 안정성 재평가** — §1(진단 재검토)의 "간헐적 실패" 결론을 다시 보면,
   차라리 실시간 API 를 캐싱(예: 성공한 응답을 DB 에 영구 보관하고 실패 시에만 캐시 사용)하는
   **혼합 전략**이 순수 파일 대체보다 나을 수 있다 — 이건 이번 게이트 범위 밖의 새 아이디어라
   따로 설계가 필요하다.
