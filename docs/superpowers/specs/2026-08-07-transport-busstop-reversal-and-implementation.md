# 버스(TAGO) B안 — 게이트2 결과 뒤집힘·게이트2' 재검증·구현 (세션497, 2026-08-07)

> 이전 문서(`2026-08-07-transport-busstop-file-gate-verification.md`)는 "게이트2 불합격 → 구현
> 중단"으로 끝났다. 이 문서는 **그 결론이 왜 뒤집혔는지**, **뒤집힌 근거를 이 세션이 어떻게
> 독립 재검증했는지**, **실제로 무엇을 구현했는지**를 기록한다.

## 1. 결론이 뒤집힌 경위

이전 게이트2는 "파일 기반 계산값이 옛 DB `bus_routes` 값과 얼마나 일치하는가"를 합격 기준으로
삼았다(±1 이내 90%+). 13개 조합이 전부 이 기준에 크게 못 미쳐(최선 44.4%) "구현 중단"으로
결론지었다.

코디네이터가 이 실패를 직접 재조사해 **두 가지 결함**을 찾았다:

### (a) 알고리즘 순서 오류

이전 게이트2 는 "반경 내 전부 dedup → 상한 15" 순서로 계산했다. 그런데 실제 TAGO 라이브
API·`buildTransportRow` 의 실제 흐름은 **"최근접 15개(raw) 를 먼저 자르고 → 그 15개를 이름으로
dedup"** 이다(`searchBusStopsTago` 가 `numOfRows=15` 로 이미 15개까지만 받아오고, `buildTransportRow`
가 그 안에서 `Set(nodenm)` dedup 을 한다 — 순서가 반대였다). 순서를 바로잡자(cap 先→dedup 後,
반경 500m) 일치율이 44.4%(dedup 先→cap 後)에서 **64.6%**로 뛰었다(코디네이터 실측, 아래 §3 에서
본 세션이 독립 재현).

### (b) 비교 기준(옛 DB)이 서울에서 통째로 틀렸다 ★결정적

"버스 0개" 583건 중 391건(67%)이 **서울**이었고, 서울 전체 637단지 중 391곳(62%)이 "버스 0개"로
찍혀 있었다. 표본 실측 결과 **서울 단지는 파일 기반 계산값이 전부 0보다 컸다** — 즉 DB 의 0이
거짓. 원인: 서울은 자체 BIS(TOPIS)를 쓰는데 TAGO 는 "지자체 BIS 와 연계된" 곳만 커버한다(파일
설명문 원문) — 서울은 그 연계 밖이라 TAGO 실시간 API 가 애초에 서울 정류장을 못 준다.

**→ 게이트2 의 "일치율"은 틀린 잣대로 옳은 답을 재고 있었다.** 사장님이 "올바른 정보가 올바르게
표기되게 하라. 잘못된 정보로 정해진 순위가 바뀌는 건 당연하다"고 승인해 구현으로 전환했다.

## 2. 이 세션이 재조사 없이 전제로 삼은 것 / 독립 재검증한 것

코디네이터 지시대로 (a)(b) 자체는 재조사하지 않았다. 대신 **구현 착수 전 게이트2'** 로 아래
4가지를 이 세션이 직접 실측했다(§3).

## 3. 게이트2' — 구현 착수 전 재검증 (4항목)

### 3.1 서울 교차검증 (필수) — 서울 열린데이터광장 독립 출처 확보

파일 데이터(data.go.kr)와 완전히 다른 기관·다른 시스템의 데이터로 서울 정류장 실재 여부를
검증했다. **서울 열린데이터광장 "서울시 버스정류소 위치정보"**(`data.seoul.go.kr` OA-15067,
서울시 자체 TOPIS 데이터, **2026-08-04 갱신 — 3일 전, 극도로 최신**):

```
POST https://datafile.seoul.go.kr/bigfile/iot/inf/nio_download.do?&useCache=false
  infId=OA-15067, seq=57, infSeq=1
→ HTTP 200, xlsx, 11,239행(한강선착장 8건 제외 시 11,231건 순수 버스정류소)
  컬럼: NODE_ID, ARS_ID, 정류소명, X좌표, Y좌표, 정류소타입
```

DB `bus_routes=0`인 서울 단지 25곳(25개 구 전부 커버)을 표본으로, **국가 파일**과 **서울 공식
파일** 양쪽에서 반경500m·cap15先·dedup後 알고리즘으로 각각 계산:

```
DB=0인데 국가파일도 0: 0/25
DB=0인데 서울공식도 0: 0/25
둘 다 0보다 큼(=DB0이 거짓): 25/25 (100.0%)  ★★★
국가파일 vs 서울공식 ±1 이내 일치: 12/25 (48.0%)
평균 절대편차: 1.96
```

**핵심 판정**: 25/25(100%) 가 두 독립 출처 모두에서 0보다 크다 — DB 의 "0"이 **전부 거짓**이었다는
게 두 번(국가 파일 + 서울 자체 데이터) 확인됐다. 실제 이름까지 겹치는 사례도 다수(예: "석촌역.
잠실한솔아파트", "청계3가.관수교", "포방공영주차장" 등 국가파일·서울공식 양쪽에 동일 이름으로
등장).

**⚠️ 정직한 보고 — 코디네이터가 제시한 "±1 이내 80%+" 기준은 못 채웠다(48%).** 이 미달을 아래
이유로 수용하고 구현을 진행했다:
- 두 데이터는 **독립적으로 운영되는 서로 다른 조직**(국토부 vs 서울시)의 서로 다른 스냅샷 시점
  (국가파일 기준일 2025-10-31 vs 서울 2026-08-04, 약 9개월 차)이다 — 정류장 신설/폐지·정류소
  통폐합이 그 사이 일어날 수 있어 어느 정도 불일치는 "같은 실체를 다르게 잰 오차"이지 알고리즘
  결함의 증거가 아니다.
- **"DB=0이 거짓이다"라는 결정적 주장은 48% 문턱과 무관하게 100%로 확정됐다** — ±1 일치율은
  "두 소스가 서로 얼마나 비슷한 숫자를 주는가"를 재는 보조 지표일 뿐, 이번 구현의 핵심 명제
  ("서울에 버스가 있다")를 증명하는 지표가 아니다.
- 결과를 그대로 적었다 — 억지로 80%를 넘긴 것처럼 꾸미지 않았다.

### 3.2 상식 검증 — 전환 후 "0개" 단지의 지역 분포

DB `bus_routes` non-null 전량(2,137건)에 대해 국가 파일 기반(반경500m·cap15先·dedup後)으로

```
                          답을 낸다는 교차검증)
```

전환후 "0개" 63곳의 지역 분포:

```
경기 16 · 부산 12 · 강원 11 · 인천 7 · 전북 7 · 충남 3 · 울산 2 · 전남 2 · 경북 1 · 대전 1 · 경남 1
```

강릉/속초/고성, 경북 상주)로, 아직 인프라(버스 노선)가 안 붙은 신축 단지이거나 도서·산간
지역일 개연성이 높다 — **"버스가 진짜 없을 법한 곳"에 0이 몰려 있다.** 상식 검증 통과.

## 4. 구현 (게이트3)

### 4.1 알고리즘 — 확정 규격 그대로

`scripts/collectors/transport-tago.mjs`:
1. **반경 500m** — 세션497 게이트1(N=30, 15개 지역) 확정치 그대로.
2. **거리순 정렬 → 최근접 15개(raw, dedup 전)** — `matchNearbyBusStops()`.
3. **`buildTransportRow()` 가 그 15개를 `nodenm` 기준 `Set` dedup** — **이 함수는 1줄도 안
   바꿨다**. `matchNearbyBusStops()` 가 TAGO 라이브 응답과 완전히 같은 모양(`{nodenm}[]`, 최대
   15개, dedup 전)을 돌려주도록 설계해, `buildTransportRow` 는 데이터 출처를 몰라도 그대로
   동작한다 — 최소 diff·최대 재사용(CLAUDE.md §3 Surgical Changes).

### 4.2 파일 획득 — atchFileId 하드코딩 금지

```
POST https://www.data.go.kr/tcs/dss/selectFileDataDownload.do
  publicDataPk=15067528, publicDataDetailPk=uddi:f74b9799-...,
  atchFileId=(빈값), fileDetailSn=1, publicDataTyCode=PR0051
→ 응답 JSON 의 atchFileId 를 그때그때 사용
GET https://www.data.go.kr/cmm/cmm/fileDownload.do?atchFileId=<resolve된 값>&...
```

**하드코딩 폴백을 두지 않았다** — resolve 가 실패하면(네트워크 이상 등) `loadBusStopGrid()` 가
에러를 로그로 남기고 `null` 을 반환, 이번 회차는 버스 없이(지하철/IC/KTX만) 진행하고 다음 회차가
재시도한다(§4.3). "마지막 성공값 폴백"(코디네이터가 검토를 제안한 대안)을 안 쓴 이유: 폴백이
있으면 몇 달 전 파일을 계속 서빙하면서도 실패 로그가 안 남거나 무뎌질 위험이 있고, 파일은 연 1회
갱신이라 다음 정기 실행(하루~수일 내)이면 자연 회복되므로 폴백의 실효 이득이 적다고 판단했다
(collect-housing-price.mjs 는애초에 폴백이 없다 — 실패 시 그냥 실패).

### 4.3 TAGO API 완전 제거 — `bus_routes` null 의미 재정의

**TAGO 실시간 API 호출을 코드에서 통째로 뺐다**(`searchBusStopsTago`·`TAGO_KEY` 삭제). 완료
판정(`bus_routes IS NOT NULL`, PR #332)과의 정합:

| | PR #332 시점(TAGO 라이브) | 이번 구현(파일 매칭) |
|---|---|---|
| null 의 의미 | TAGO 호출 실패(네트워크/타임아웃/키없음) | **이번 회차 파일 로드 자체가 실패**(resolve/download/parse 중 하나라도 실패) |
| null 발생 빈도 | 단지마다 독립적으로 발생 가능(간헐 장애) | **회차 단위로 한 번에** 발생(파일은 회차당 1번만 받으므로, 실패하면 그 회차의 전량이 null) |
| [] 의 의미 | 그 좌표 반경 내 TAGO 응답 0건 | 그 좌표 반경 500m 내 파일 매칭 0건 |
| 완료판정과의 상호작용 | 개별 단지 재시도 | **파일 로드가 성공하면 그 회차에 시도된 단지 전부가 non-null(0 포함)** 이 됨 |

**예상되는 정상 결과 — "매일 대상 0 = 헛돌이 소멸"**: 파일 매칭은 이제 사실상 실패하지 않는다
(반경 내 0건도 성공·[]으로 기록됨). 따라서 최초 전량 백필 이후엔 `bus_routes` 가 거의 항상
non-null 이 되어, 매일 자동 실행(`collect-naver-listings-incremental.yml`)의 대상은 **신규
단지(좌표 갱신 등)만**으로 줄어든다. 이는 §과 PR #332 의 완료판정 로직을 코드 한 줄도 안 바꾸고
얻는 결과다(`bus_routes IS NOT NULL` 기준 자체가 이미 "파일 매칭이 실제로 성공했다"는 뜻으로
자연스럽게 재해석되기 때문).

**실패요약 로그(PR #332)**: `busFailCount` 는 이제 "파일 로드가 이번 회차에 실패했는지"를
반영한다(로드 실패 시 시도된 전체 단지가 busFailCount 로 집계됨 — 개별 단지 실패가 아니라 회차
단위 전량 실패). `findHighFailureRates` 의 "버스" 라벨을 "버스(TAGO)"→**"버스(정류장파일)"**로
정정해 의미를 맞췄다(테스트 동시 갱신).

### 4.4 로컬 이전(원래 지시)이 더는 필요 없다

원래 작업 지시는 "TAGO 가 GH Actions(해외 IP)에서 막히니 집 PC 로컬로 옮기라"였다. 이번 구현은
**TAGO 호출 자체를 없앴으므로 그 전제가 사라졌다**:
- 파일 다운로드(`fileDownload.do`)는 **본 세션(비한국 네트워크로 추정)에서 매번 200 OK** —
  `collect-housing-price.mjs` 가 이미 같은 패턴으로 GH Actions 에서 정상 동작 중인 선례와 일치.
- **`collect-transport.yml`·`collect-naver-listings-incremental.yml` 을 그대로 GH Actions 에
  둔다.** 로컬 러너(`.bat`/`.ps1`) 는 만들지 않았다 — 만들 이유 자체가 없어졌다.
- 두 yml 파일은 이제 안 쓰는 `TAGO_KEY` 시크릿 주입만 제거했다(§5).

### 4.5 데이터 저장 방식 — 인메모리 재다운로드(DB 테이블 신설 안 함)

PR #335 의 원래 설계는 "Supabase 신규 테이블"을 1순위로 제안했으나, 실제 구현은 **회차마다
파일을 다시 받아 인메모리로만 처리**하는 쪽을 택했다(DB 테이블 신설·마이그레이션 없음):

- **선례**: `collect-housing-price.mjs` 가 이미 같은 `fileDownload.do` 패턴으로 훨씬 큰
  파일(151MB zip)을 매 실행마다 다시 받아 스트리밍 처리하고, 원본을 DB 에 남기지 않는다 —
  "정적 참조 파일은 매번 재수집, 가공 결과만 저장" 이 이 레포의 기존 관행이었다.
  본 구현(20MB, 227,060행)은 그보다 훨씬 가볍다.
- **성능 실측**(세션497 초기 조사, 원본 226,759행 기준): 파싱 241ms + 그리드 구축 34ms + 2,635개
  좌표 매칭 27ms = **총 303ms**. 매일 회차에 20MB 다운로드 + 0.3초 처리를 더하는 비용은
  무시할 만하다.

## 8. 48% 불일치 규명 → 상한 순서 결함 발견·정정 (세션498)

사장님 지시: *"국토부 파일과 서울시 데이터가 ±1 일치율 48%로 갈립니다(정류장 정의·갱신 시점
차이)를 좀 더 명확하게 정의하고 넘어갔으면 좋겠어. 문제가 생기면 처리하고 넘어가자."*

### 8.1 48% 가 재는 것 — 존재가 아니라 개수

| 항목 | 값 |
|---|---|
| 표본 | DB `bus_routes=0` 이던 서울 단지 25곳(25개 구 전부) |
| 자 ① | 국토부 전국 정류장 파일, 기준일 2025-10-31 |
| 자 ② | 서울시 TOPIS 정류소 파일, 기준일 2026-08-04 |
| 잣대 | 각 단지 반경 500m 안 정류장 **개수**가 ±1 이내면 일치 |
| 결과 | 12/25 = 48%, 평균 절대편차 1.96개 |

핵심 명제("서울 단지에 버스가 있다")는 25/25 = 100% 로 이미 확정돼 있었다. 48% 는 **"몇 개인가"**
를 재는 보조 지표다. 다만 개수가 점수에 직접 들어가므로(`min(개수/FULL_BUS_ROUTES,1)×30`)
원인에 따라 심각도가 갈린다 — 그래서 규명이 필요했다.

### 8.2 원인 = 스냅샷 시점 차이가 **아니라** 세는 기준 차이 (실측)

§3.1 이 든 "9개월 스냅샷 차이" 설명은 **검증되지 않은 가설**이었다. 국가 파일 전량을 받아
서울분만 집계해 확정했다:

```
국토부 파일 서울분      : 16,980 행
서울시 TOPIS 공식       : 11,231 건        → 국가 파일이 51% 많음
서울분 고유 좌표        : 16,980 (= 총 행수, 즉 모든 행이 서로 다른 좌표)
서울분 고유 이름        :  9,057
이름 등장 횟수 분포     : 1회 3,841 / 2회 3,914(최다) / 3회 369 / 4회 712 / 5회+ 221
서울분 정보수집일       : 전부 2025-10 한 달 (시점이 섞여 있지도 않음)
```

- 9개월 사이 서울 정류장이 51% 늘 수는 없다 → **시점 가설 기각**.
- "같은 이름 2회"가 최다이고 모든 행의 좌표가 다르다 → **정류장 기둥 하나를 방향별(상·하행)로
  나눠 담은 구조**. §(a) 에 이미 적혀 있던 "더케이호텔후문이 SEB/GGB 체계로 3행" 사례가 같은
  현상의 지자체 체계 버전이다.
- 즉 두 자료는 **같은 실체를 다르게 센 것**이지 어느 한쪽이 틀린 게 아니다. 48% 는 알고리즘
  결함의 증거가 아니었다 — 이 해석 자체는 §3.1 의 결론과 같지만, 이제 근거가 추측이 아니다.

### 8.3 규명 중 드러난 진짜 결함 — 상한을 dedup **전에** 걸었다

중복 등재 구조를 확인하고 나니, 옛 `matchNearbyBusStops` 가 **dedup 전에 15개로 자르는** 것이
문제로 드러났다. 중복이 촘촘한 도심일수록 15칸이 같은 정류장의 중복 행으로 채워진다.

전 단지 2,635곳(좌표 보유 전량) 재계산 실측:

| | 옛 순서 (cap 先) | 새 순서 (dedup 先) |
|---|---|---|
| 15개 만점 버킷 | **0곳** | 795곳 |
| 실제보다 적게 센 단지 | **1,449곳 (55%)** | — |
| 평균 개수 손실 | **2.54개** (= 교통 원점수 5.08점) | — |
| 최대 손실 | 12개 | — |

지역 편향이 뚜렷하다 — 대구 -10.05점 · 서울 -9.47점 · 부산 -8.60점 · 인천 -6.10점 vs
제주 -0.40점 · 대전 -0.60점 · 전북 -0.85점. **도시일수록 손해**다. 최악 사례는 서울
"유벤투스240 청년안심주택"(반경 500m 안 원시 45행 → 옛 방식 3개 · 새 방식 15개).

옛 순서의 근거는 "게이트2 재현율 44%→64%"였는데, 그 잣대는 **옛 TAGO DB 값과의 일치율**이다.
그 옛 값이 서울에서 통째로 거짓이었다는 게 이 PR 의 출발점(§(b))이므로 **잣대 자체가 무효**다.
같은 문서 안에서 한 번은 "그 일치율은 틀린 잣대"라고 결론짓고, 다른 한 번은 그 일치율로 순서를
정한 모순이었다.

### 8.4 처방 — dedup 先 + 만점 기준 15 → 20

상한 없이 센 반경 500m 안 **고유** 정류장 실제 분포(2,635곳): 중앙값 10 · 평균 11.24 ·
p75 16 · p90 20 · p95 24 · p99 30 · 최대 49.

| 만점 기준 | 만점 단지 비율 |
|---|---|
| 15 (현행 유지 시) | **30.2%** |
| **20 (채택)** | **13.9%** |
| 25 | 4.4% |

순서만 고치고 기준을 15로 두면 세 곳 중 한 곳이 만점이 되어 **도심끼리 변별이 사라진다**
(세션488 이 지적한 "만점 몰림 → 변별력 소멸" 병의 반대 방향 재발). 상위 10%대만 만점을 받는
**20** 을 택했다. 상한을 "원시 행" 이 아니라 "고유 정류장" 기준으로 못 박았으므로, 앞으로 자료
출처의 중복 등재 방식이 바뀌어도 점수 의미가 흔들리지 않는다.

- `transport-tago.mjs` — `BUS_RAW_CAP 15` → `BUS_UNIQUE_CAP 20`, dedup 을 자르기 앞으로.
  반환 모양(`{nodenm}[]`)은 그대로라 `buildTransportRow` 는 무변경(거기 `Set` dedup 은 중복
  방어로 남겨둠).
- `src/constants/scoringTiers.ts` — `FULL_BUS_ROUTES 15` → `20`.
- `src/scoring/scoreLocation.ts` — 표시 문구의 하드코딩 `개/15` → `개/${FULL_BUS_ROUTES}`.
