## 1. 진단 재검토 — "해외 IP 차단" 단정 철회

### 1.1 원래 가설 (KOSIS·childcare 선례 답습)

`scripts/CLAUDE.md` "KOSIS 수집 — 로컬 자동화"·"childcare 수집 — 로컬 자동화" 절의 선례는 둘 다 **해당 API 호스트 전체가 GitHub 러너(해외 Azure IP)를 차단**한 사고였다(kosis.kr 전체 실패, api.childcare.go.kr 전체 실패). transport-tago.mjs 의 TAGO 실패도 처음엔 같은 패턴으로 보였다.

### 1.2 결정적 모순 — collect-maintenance 가 같은 게이트웨이로 정상 수집

`collect-maintenance.mjs:42` 의 API 베이스:
```

```
transport-tago.mjs 의 TAGO 베이스(`transport-tago.mjs:78`):
```
https://apis.data.go.kr/1613000/BusSttnInfoInqireService/getCrdntPrxmtSttnList
```
**호스트(`apis.data.go.kr`)와 기관 코드(`1613000` = 국토교통부)가 완전히 같다.**

라이브 실측(`gh run view 31129313072 --log`, run 시작 2026-08-06T22:53:44Z):
```
2026-08-07T00:54:24.4324237Z [maintenance] [완료] 1567.3초 | 성공 257 | 실패 0 | 스킵 343 | 총 600건
2026-08-07T00:54:24.4324850Z [maintenance] API 호출: 3160회
```
같은 시각대(00:5x Z)에 관리비 수집이 **600건 전량 정상**(성공 257·스킵 343·실패 0)으로 끝났다 — 스킵은 이미 최근 수집된 건이라 재조회를 생략한 것이지 실패가 아니다. 같은 15분 남짓한 창에서 transport 는 전멸했다(작업 지시서 표 참조: 08-06 22:09 버스 369/369 전멸, 08-07 04:35/04:43 도 전멸).

**IP·네트워크 레벨 차단이면 같은 게이트웨이의 다른 서비스도 죽어야 한다. 그러지 않았다.** 따라서 "해외 클라우드 IP 차단"(KOSIS·childcare 식)은 **입증되지 않았다** — 오히려 **서비스별(엔드포인트별) 정책 차이**가 더 정합적인 설명이다. TAGO 의 `getCrdntPrxmtSttnList` 는 실시간 대중교통 위치 조회라 캐싱이 어렵고, 지자체 BIS(버스정보시스템) 연계 구조라 스크래핑성 트래픽에 더 민감한 스로틀/우선순위 저하가 걸릴 가능성이 있다 — 단 이것도 **가설**이지 확정이 아니다.

### 1.3 기각된 보조 가설 — IPv6 우선 시도

`apis.data.go.kr` 의 DNS 레코드를 확인한 결과 **A(IPv4) 레코드만 존재**(`27.101.236.63`), **AAAA(IPv6) 레코드는 없다**. "GitHub 러너가 IPv6 를 먼저 시도하다 멈춘다" 류의 가설은 애초에 IPv6 경로 자체가 없으므로 **기각**한다. 다음 사람이 같은 가설을 다시 조사하지 않도록 여기 남긴다.

### 1.4 KOSIS·childcare 선례와의 차이 (표)

| | KOSIS | childcare | transport(TAGO) |
|---|---|---|---|
| 실패 범위 | 호스트 전체(kosis.kr) | 호스트 전체(api.childcare.go.kr) | **같은 게이트웨이의 다른 서비스는 정상** |
| 실패 양상 | 연속·전면 | 연속·전면 | 간헐적(08-05 정상 3.99초/단지 → 08-06 전멸 → 08-07 정상/전멸 반복) |
| 원인 확정도 | 확정(로컬 재현 200 OK) | 확정(로컬 재현 200 OK) | **미확정** — 로컬 재현 200 OK 는 확인됐으나(작업 지시서 04:45 행), 같은 게이트웨이 타 서비스가 GH 러너에서 살아있다는 반증도 동시에 있음 |
| "로컬 이전하면 해결" 확신도 | 높음(선례 실증) | 높음(선례 실증) | **낮음** — IP 문제가 아니라면 로컬 이전도 안 통할 가능성 있음(다만 한국 IP가 지자체 BIS 스로틀에서 더 우대받을 가능성은 있어 완전 배제는 아님) |

이 표의 마지막 줄이 A안(선례 답습)을 그대로 밀어붙이면 안 되는 이유다 — **원인이 IP 가 아니라면 로컬로 옮겨도 똑같이 실패할 수 있다.** 반면 B안(파일 기반)은 원인이 무엇이든 **TAGO 실시간 API 호출 자체를 없애므로** 원인 불확정 상태에서도 유효한 해법이 된다.

### 2.4 점수 영향 — 정면으로 다룬다 (가장 중요한 절)

#### 2.4.1 지금 bus_routes 는 점수에 직접 들어간다

```ts
// src/scoring/scoreLocation.ts:64,69
const busRoutes = (apt.busRoutes ?? 0) as number;
const rawBus = Math.min(busRoutes / FULL_BUS_ROUTES, 1) * 30;
```
```ts
// src/constants/scoringTiers.ts:30
export const FULL_BUS_ROUTES = 15;
```
`FULL_BUS_ROUTES = 15` 는 **TAGO API 의 `numOfRows=15` 하드캡과 같은 숫자**다(우연이 아니라 API 응답 최대치에 맞춰 만점 기준을 잡은 것). `busRoutes` 는 6개 카테고리 중 "입지" 카테고리(가중치 0.30 중 버스 서브가중치 `ct.busW`, 도시등급별 상이)의 최대 30점을 좌우한다. 화면에도 그대로 노출된다(`scoreLocation.ts:134,144`):
```
버스 {busRoutes}개                (요약)
버스 {busRoutes}개/15             (상세 — "/15" 가 캡을 그대로 노출)
```
**→ 정의(반경·집계 방식)가 바뀌면 전체 단지의 입지 점수와 화면 표기가 바뀐다.** 이걸 흔들지 않는 것이 이번 전환의 최우선 목표다.

#### 2.4.2 현행 분포 (DB 실측 — bus_routes non-null 2,137건)

| 구간 | 건수 | 비율 |
|---|---|---|
| 0개 | 583 | 27% |
| 1~4개 | 336 | 16% |
| 5~9개 | 874 | 41% |
| 10~14개 | 344 | 16% |
| **15개(만점 상한 도달)** | **0** | **0%** |

**아무도 상한에 안 닿아 변별력이 살아 있다.** 이건 [[composition-root-not-bloat]] 류가 아니라 `.claude/rules/` 에 아직 별도 이름은 없지만, 세션488 전면감사가 지적한 "시설 개수 지표가 최대치에서 절단돼 만점자가 72~87%로 몰려 변별력이 죽는" 병과 **같은 계열의 위험**이다. **파일 기반으로 반경을 넉넉히(예: docstring 이 말하는 "1km") 잡으면 다수가 15를 넘겨 전부 만점 처리되고, 변별력이 소멸한다.** 이 실수를 반복하지 않는 것이 반경 설계의 핵심 제약이다.

#### 2.4.3 암묵 반경 역산 (표본 3건 — provisional, N≥20 필요)

TAGO API 는 반경 파라미터를 받지 않는다(`getCrdntPrxmtSttnList` 는 `gpsLati/gpsLong/numOfRows` 만 받음 — WebSearch 로 공식 문서에서 별도 radius 파라미터를 확인 못 함). 그런데도 응답 정류장 수가 지역마다 0~15로 들쭉날쭉한 걸 보면 서버 내부에 실제 거리 상한이 있다는 뜻이다. 표본 3건의 응답 좌표로 거리를 역산한 결과:

| 단지 | DB 개수 | API 반환 수 | 최소거리 | 최대거리 |
|---|---|---|---|---|
| 인천 계양 하늘채 파크포레 | 2 | 4 | 314m | **451m** |
| 부산 에코델타시티 푸르지오린 | 5 | 10 | 178m | **453m** |
| 대구 동대구역 엘크루 | 8 | 15(캡) | 41m | 278m(캡에 잘려 최대거리 의미 없음) |

캡에 걸리지 않은 두 표본의 최대거리가 **451m·453m로 거의 일치** — **암묵 반경 ≈ 450~500m**(도보 5~7분권)로 추정한다. 파일 헤더 주석(`transport-tago.mjs:5` "버스(TAGO 좌표기반, **1km**)")은 실측과 안 맞는 **아마도 아스퍼레이셔널한(의도했지만 코드로 강제하지 않은) 값**이다 — 실제 상한을 만드는 건 API 서버 내부 로직이지 우리 코드가 아니다. **B안은 이 docstring 의 "1km" 가 아니라 실측 450~500m 를 재현 목표로 삼아야 한다.**

⚠️ **표본이 3건뿐이다.** 구현 착수 전 §2.5 절차로 N≥20(가능하면 지역별 층화 표본)으로 재확정해야 한다 — 지금 450~500m 는 방향성 확인용이지 최종 확정값이 아니다.

#### 2.4.4 정류장 개수 집계 방식 — 이름 기준 중복 제거

```js
// transport-tago.mjs:109-113
const busStopNames = busStops === null ? null
  : [...new Set(busStops.map(d => d.nodenm).filter(Boolean))];
const busRoutes = busStopNames === null ? null : busStopNames.length;
```
`nodenm`(정류장명) 기준 **`Set` 중복 제거**다. DB 개수가 API 반환 수의 대략 절반인 이유(인천 4→2, 부산 10→5, 대구 15→8 — 정확히 근사 절반)는 **같은 물리적 정류장이 상행/하행 2개 노드로 따로 잡히는데, 이름이 같아서 하나로 합쳐지기 때문**이다.

**⚠️ 이 dedup 로직을 파일 데이터에 그대로 이식하면 다른 결과가 나올 수 있다 — 본 세션에서 실측으로 확인.** 아래 §2.5 실제 사례를 보라: 같은 물리적 위치(13m 이내)의 상행/하행 쌍인데 **정류장명 문자열이 서로 다르다**(구성 요소 순서가 뒤바뀜). API 응답에서는 두 방향 노드가 같은 `nodenm` 을 공유하는 경우가 많아 보이지만, 파일 데이터는 그 보장이 없다. **정류장명 완전일치 dedup 을 파일에 그대로 포팅하면 API 값보다 개수가 더 많이(중복 제거가 덜) 나올 위험이 있다.** 좌표 근접 기준(예: 반경 30~50m 이내 정류장을 1개로 묶기) 이 더 안정적인 대안일 수 있으며, **§2.5 검증 절차에서 반경뿐 아니라 이 dedup 전략도 함께 튜닝**해야 한다.

#### 2.4.5 재현 목표 (요약)

파일 기반으로 **현행과 사실상 같은 값**을 만들려면 다음 3개를 최대한 재현한다(이번 전환의 목표는 **점수 변화 ≈ 0**, 지표 개선이 아니다):

1. **반경 450~500m**(정확한 값은 N≥20 재역산으로 확정 — §2.5)
2. **정류장 dedup** — 이름 완전일치가 아니라 **좌표 근접 기준으로 대체 검토**(§2.4.4 근거)
3. **상한 15**(`FULL_BUS_ROUTES` 와 정합 유지)

**"이 참에 지표를 개선하자"(예: 최근접 정류장까지의 거리로 바꾸기)는 별도 후보로만 제시하고 이번 전환과 절대 섞지 않는다** — 전환(같은 지표를 다른 소스로)과 지표 변경(다른 지표로)을 동시에 하면 회귀가 나도 원인을 못 가른다.

### 2.5 TAGO 라이브 커버리지 불안정 vs 파일 — 실측 사례 (의왕 더샵캐슬)

표본 중 **경기 의왕 더샵캐슬**은 DB 에 12개가 저장돼 있는데, 오늘(2026-08-07) 한국 IP 에서 TAGO API 를 다시 호출하면 **0건**을 반환한다(코디네이터 실측). "TAGO 는 지자체 BIS 연계 상태에 따라 커버리지가 시간·지역별로 흔들린다"는 걸 뒷받침한다(파일 설명문도 "BIS 가 구축되고 TAGO 와 연계된 지자체"라고 조건부로 적어놨다 — 연계가 끊기면 그 지자체 정류장 전체가 실시간 API 에서 사라질 수 있다는 뜻).

**이 파일에 그 좌표 인근 정류장이 있는지 직접 확인했다** — 있었다:

```
GGB226000220,대명구름채.더샵캐슬아파트.경기중앙교회,37.3612333,126.9667333,2025-10-31,27216,31170,경기도 의왕시,경기BIS
GGB226000221,더샵캐슬.대명구름채아파트.경기중앙교회,37.3611333,126.96665,2025-10-31,27217,31170,경기도 의왕시,경기BIS
```

정류장명에 **"더샵캐슬"이 문자 그대로 들어 있는 두 정류장**이 존재하며, 두 좌표 간 거리는 약 13m — 같은 물리적 정류장의 상/하행 쌍으로 보인다(§2.4.4 에서 이 쌍의 이름이 서로 다르다는 걸 근거로 dedup 전략을 재검토한 것도 이 실측에서 나왔다).

**→ 파일 기반이 TAGO 의 오늘자 실시간 장애(0건 응답)를 보완하는 실증 사례.** 단, 한계도 명확히 적는다: 파일도 **연 1회 스냅샷**이라 신설 정류장·노선 변경엔 최대 1년 지연이 있고, "오늘 이 순간의 실제 상태"를 반영하지 못한다. TAGO 실시간 API 가 정상 작동하는 지자체에 대해서는 파일이 오히려 더 낡은 정보일 수 있다 — **정적 인프라(버스정류장 위치)라 이 지연이 감내할 만하다**는 것이 이 트레이드오프를 받아들이는 전제다.

### 2.6 이 안이 성립하면 "로컬 이전" 자체가 불필요해질 수 있다

§1 에서 "IP 차단"을 단정할 수 없다고 결론 내렸다. B안은 원인이 무엇이든(IP 차단이든 서비스별 스로틀이든) **TAGO 실시간 API 호출을 아예 없애므로** 원인 불명 상태에서도 유효하다. 게다가:

- §2.1 에서 확인한 파일 다운로드는 **본 에이전트 환경(비한국 네트워크로 추정)에서 익명 200 OK** 로 성공했다.
- `collect-housing-price.mjs` 가 이미 같은 `fileDownload.do` 패턴으로 **GitHub Actions(해외 러너)에서 정상 동작 중**이다(세션247 실증, 별도 이전 없이 GH 에 남아 있음).

**→ B안이 검증을 통과하면, 굳이 로컬 PC 로 옮길 필요 없이 GH Actions 위에 그대로 둘 수 있다.** 다만 이건 "가능성이 높다"이지 확정이 아니다 — 실제로는 workflow_dispatch 로 GH 러너에서 1회 시험 다운로드를 해봐야 한다(§9 Go/No-Go).

### 2.7 저장·매칭 설계

#### 2.7.1 저장 위치

| 안 | 장단점 |
|---|---|
| **Supabase 신규 테이블**(`bus_stops_raw` 등, 206k~227k행 × 9열) | 쿼리 가능·영속·마이그레이션 1개로 관리. Postgres 에 이 정도 행수는 부담 없음(이미 `articles` 131만행 운용 중). **추천** |
| gitignored 로컬 캐시 파일(연 1회 재다운로드, staleness 체크) | DB 스키마 변경 없이 시작 가능. 단 collector 실행 환경마다(로컬/GH) 별도로 캐시해야 하고 "파일이 최신인가"를 매번 판정하는 로직이 필요 |
| `public/data/*.json` 커밋 | **기각** — 20MB급 파일은 이 디렉토리의 기존 파일들(4~9KB, `transit-dev.json` 등)과 스케일이 다르다. `public/` 은 클라이언트에 서빙되는 정적 자산 디렉토리라, 손님 브라우저가 이 파일을 받을 이유가 없는데 번들에 섞일 위험이 있다. 매년 갱신마다 diff 노이즈도 크다 |

#### 2.7.2 매칭 알고리즘 — 그리드 인덱스 + haversine

기존 레포에 `transit-match.mjs` 선례가 있으나(정류장 몇백 개 규모의 소형 시드 vs 아파트를 O(N×M) 이중루프로 순회) 이번 규모(정류장 20만+ × 아파트 2,635)에 그대로 쓰면 haversine(삼각함수 포함) 연산이 최대 5억 회를 넘어 느릴 수 있다. **그리드 인덱스**(위경도를 0.01도 셀로 나눠 버킷팅, 반경 500m 조회 시 자기 셀+인접 8셀만 확인)로 O(N) 전처리 + O(M×후보수) 조회로 낮춘다.

**실측 벤치마크**(본 세션, 다운로드한 실제 CSV 226,759행 + 위경도 시뮬레이션 좌표 2,635개 — ⚠️ 시뮬레이션 좌표는 실제 apartments 테이블 좌표가 아니라 주요 도시 주변 임의 분포 근사치, **성능 자릿수 확인용**이지 정확한 매칭 결과가 아니다):

```
CSV 파싱(EUC-KR 디코딩 포함): 226,759행, 241ms
그리드 인덱스 구축(0.01도 셀, 39,741개 셀): 34ms
2,635개 좌표 × 반경 1km 조회 + haversine 정렬: 27ms
전체 파이프라인: 303ms
```

**외부 API 호출 없이 3,600여 개 단지를 1초 이내에 처리** — 현재 TAGO 정상 시(3.99초/단지) 기준 498건에 약 33분 걸리는 것과 비교가 안 되게 빠르다. `haversineKm`(`_shared.mjs:108`)을 그대로 재사용하면 되고, 그리드 인덱스는 노드 표준 `Map` 만으로 충분해 새 의존성이 필요 없다.

### 2.8 재현 검증 절차 (구현 착수 전 의무 — §2.4.5 의 3개 값을 확정하는 절차)

1. **표본 N≥20**(지역별 층화 — 대도시/중소도시/지방 섞어서) apartments 에 대해 TAGO 라이브 API 값(`busRoutes`, `bus_stop_names`)을 실측.
2. 같은 표본에 대해 파일 기반 계산값을 여러 (반경, dedup 전략) 조합으로 산출 — 예: 반경 {400,450,500,550}m × dedup {이름 완전일치, 좌표근접 30m, 좌표근접 50m}.
3. 조합별 **일치율**(개수가 ±1 이내로 맞는 비율)과 **오차 분포**를 표로 비교, 가장 잘 맞는 조합을 채택.
4. **채택한 조합으로 전체 DB(2,137건)에 대해 파일 계산값을 산출**, 기존 `bus_routes` 분포(§2.4.2 표)와 나란히 비교 — 분포 형태가 크게 안 달라야 한다(특히 "15개 만점" 비율이 0%에서 크게 안 튀는지 확인).
5. **scoring 영향 대조** — 표본(또는 전체) 단지에 대해 기존 총점과 전환 후 총점의 차이 히스토그램을 뽑는다. 대다수가 ±1~2점 이내여야 "점수 변화 ≈ 0" 목표를 만족한다고 볼 수 있다.
6. `_noBus` 처리 재정의 — 지금은 TAGO 호출 실패(null)와 성공·0건([])을 구분해 `_noBus = busStopNames == null` 로 "미수집"을 표시한다(`transport-tago.mjs:97-98`, `engine.ts:106-109`). 파일 기반은 항상 "계산 가능"(파일 자체가 없거나 좌표가 없는 경우를 빼면 실패라는 개념이 옅어진다) — 이 차이가 `_noBus` 배지·스코어링 안전망에 미치는 영향을 §2.4.1 흐름과 함께 재정의해야 한다.

이 절차를 통과하기 전엔 구현에 착수하지 않는다(§9 Go/No-Go 의 B 트랙 조건).

## 3. 후보 A — 집 PC 로컬 러너 이전 ("A안 채택 시" 조건부 상세설계)

> §1 의 진단 재검토로 "IP 차단이라 로컬로 옮기면 해결된다"는 전제가 약해졌으므로, A안은 **B안이 기술적으로 막힐 때의 백업안**으로 격을 낮춘다. 아래는 원래 지시대로 조사한 전체 세부설계 — B가 막히면 이 내용을 그대로 쓴다.

### 3.1 이전 범위 판정

transport-tago.mjs 는 단지당 4개 외부 호출을 한다: 카카오 지하철(SW8)·**TAGO 버스**·카카오 IC·카카오 KTX. 카카오 3종은 GH 러너에서 정상, TAGO 만 문제(라고 원래는 생각했다 — §1 참조).

| 안 | 요지 | 코드 변경량 | 실패 모드 | 되돌리기 |
|---|---|---|---|---|

## 6. D안 비용 정량 산정

주어진 값: 실패 시 21.6초/단지(작업 지시서 04:35 관측), 대상 498건, `--budget-min` 상한(collect-transport.yml 50분 / incremental.yml 기본 180분), 세션491 실측 단가 $0.006/분(비공개 레포 공유 월 2,000분 초과분).

**시나리오: TAGO 가 회복되지 않고 매일 이 상태가 반복된다고 가정**(완료판정이 `bus_routes IS NOT NULL` 이라 실패가 계속되면 같은 단지가 계속 "미수집"으로 남아 매일 재시도 대상에 들어온다 — PR #332 의 `orderTargets` 가 신규를 우선하지만 신규 유입이 적으면 총 대상 규모는 ~498 근처로 유지된다고 가정).

```
실패 시 전체 소요 = 498건 × 21.6초 = 10,756.8초 = 179.28분
```
`incremental.yml` 의 transport 스텝 기본 예산(180분, --budget-min 인자 없음)과 **거의 정확히 일치**한다 — 즉 지금 이 순간 매일 실행되는 transport 스텝이 **예산을 거의 다 채울 때까지 전부 실패하며 도는 상태**라는 뜻이다.

건강한 기준선(08-05 20:48 정상 관측, 324건 3.99초/단지 → 498건 환산):
```
건강 시 소요 = 498건 × 3.99초 = 1,986초 = 33.1분
```
**하루 낭비 시간 = 179.28분 − 33.1분 = 146.18분**

**월간(30일) 낭비 = 146.18 × 30 = 4,385.4분**

**월간 비용 = 4,385.4분 × $0.006/분 ≈ $26.31**

이건 **최악에 근접한 상한선**이다 — `budgetExceeded`(180분)가 사실상의 캡이라, 개별 호출이 21.6초든 그보다 더 느린 38.8초(04:43 관측)든 스텝 자체는 180분에서 끊긴다(더 느리면 처리 건수가 줄 뿐 스텝 시간은 안 늘어난다). 그래서 "월 $26 언저리"는 시나리오 안에서 비교적 안정적인 숫자다.

**⚠️ 비용보다 더 심각한 리스크 — job timeout 충돌**: `collect-naver-listings-incremental.yml` 의 240분 job timeout 은 원래 "transport 64분 + infra 21분 + schools 최악 134분 = 219분, 마진 21분"으로 설계됐다(파일 자체 주석). TAGO 가 계속 실패하면 transport 가 64분이 아니라 **179분**을 쓰므로, **schools 가 NEIS 30일 전수 갱신과 겹치는 날엔 179+21+134=334분 > 240분 job timeout** 을 넘길 수 있다. job timeout 은 grace 0 SIGKILL 이라(`.claude/rules/collectors/graceful-shutdown-coverage.md` 실증) **schools 의 부분 진행 기록조차 못 남기고 죽을 위험**이 있다 — 이건 돈이 아니라 **데이터 결측**으로 이어지는 문제라 D안의 진짜 비용은 $26/월보다 크다.

**전제 명시**: 위 계산은 "TAGO 가 영구 회복 안 됨" + "백로그 규모가 ~498 근처로 유지됨"을 가정한다. §1 의 실측(08-05 정상, 08-06 전멸, 08-07 혼재)을 보면 TAGO 는 완전 영구 장애가 아니라 **간헐적**이라 실제 월간 낭비는 이보다 작을 수 있다 — 단 "얼마나 자주 살아나는지"는 미확정이라(§9 Go/No-Go), 낭비액이 0에 수렴한다고 가정할 근거도 없다.

## 8. 추천안과 근거

**1순위: B (파일 기반 전환)**, 조건부(§2.8 검증 통과 후 착수).

근거:
1. §1 의 진단 재검토로 "로컬 이전=해결"이라는 A안의 전제 자체가 흔들렸다 — **원인 불명 상태에서도 유효한 해법은 B뿐**이다(TAGO 호출을 아예 없애므로).
2. §2.5 에서 TAGO 의 실시간 커버리지 불안정(의왕 사례, DB 12개·API 0건)을 파일이 보완하는 실증을 직접 확인했다 — B는 단순 "차단 우회"가 아니라 **지금 API 자체보다 더 안정적일 가능성**이 있다.
3. §2.6 대로면 **로컬 이전 자체가 필요 없어질 수 있다** — 집 PC 의존(무인 상태·전원·네트워크 등 새 단일장애점)을 늘리지 않아도 된다.
4. §2.7 벤치마크로 성능 문제가 없음을 확인했다(외부 API 0회, 1초 미만).
5. 운영비 관점에서도 D(월 $26+ 낭비+timeout 위험)보다 명백히 낫고, A보다도 GH 잔류가 가능해 인프라 단순성이 높다.

**단 §2.8 검증(반경·dedup 재현, 점수 변화 대조)을 통과하기 전엔 착수하지 않는다** — 이게 이 추천의 유일한 전제조건이다. 검증에서 재현이 어렵다고 판명되면(예: 반경을 아무리 튜닝해도 일치율이 낮다), **A(로컬 이전)로 후퇴**한다 — A의 세부설계(§3)는 그 경우를 위해 이미 완성해뒀다.

**C 는 기각하지 않고 병행**: B 검증에 시간이 걸리는 동안(며칠~1~2주) 매일 반복되는 낭비를 줄이는 임시 완화로 붙여도 된다 — 단 이번 PR 의 범위는 아니며 별도로 판단.

**D 는 기각**: §6 의 비용(월 $26+) + job timeout 데이터 결측 위험이 "아무것도 안 함"의 실제 대가다.

## 9. Go/No-Go 관측 기준

### B 트랙 (1순위)

1. **파일 다운로드가 GH Actions 러너(해외 IP)에서도 통하는지** — `workflow_dispatch` 로 §2.1 의 URL 을 1회 시험 다운로드(가벼운 HEAD 요청이면 충분, 코드 작성 없이 curl 스텝만으로도 확인 가능). 200 OK + Content-Length 일치 → GO(§2.6 대로 GH 잔류 가능). 지역 차단 발견 시 → 로컬 PC 에서만 다운로드하는 절충안(주기적으로 로컬이 받아 Supabase 에 적재, 이후 매칭은 GH 에서도 DB 조회로 가능 — 어느 쪽에서 받든 다운로드는 연 1회뿐이라 부담 작음).
2. **§2.8 재현 검증 통과** — N≥20 표본 일치율이 납득할 수준(예: 개수 ±1 이내 일치율 80%+, 이 임계는 실제 표본을 보고 사장님과 함께 정하는 게 안전 — 지금 숫자로 못 박지 않는다)이고, 전체 DB 대조 시 분포 형태(§2.4.2)와 총점 변화(±1~2점 이내가 대다수)가 문제없으면 → **GO, 구현 착수**.
3. 반경·dedup 을 아무리 튜닝해도 일치율이 낮거나(예: 대부분 ±3개 이상 벗어남), 15개 만점 비율이 크게 튀어 변별력이 죽으면 → **NO-GO, A로 전환**.

### A 트랙 (B가 막혔을 때만)

`external-api-outage-policy.md`·`collector-timeout-rootcause-analysis.md` 의 기존 패턴(3연속 관측)을 그대로 따른다: PR #332 가 남기는 `호출 실패 요약: ... 버스(TAGO) ...` 로그와 `⚠️ 실패율 R% — 외부 API 장애 의심(임계 50%)` 경고를 **GH Actions 대장애(8-06~8-07) 종료 후** 자연 발화(매일 KST 05:30) 기준 **3회 연속** 관찰한다.
- 3회 모두 임계(50%) 초과 유지 → 간헐적이 아니라 사실상 상시 실패로 재확정, A 착수.
- 3회 중 2회 이상 임계 밑으로 떨어지면 → §1 그대로 "간헐적"으로 재확인, 로컬 이전의 효과도 불확실해지므로 **C(쿨다운)만으로 당분간 충분한지 재검토**.

**공통**: 어느 트랙이든, 오늘(2026-08-07)의 관측치는 GH Actions 대장애(8-06 18:00Z~8-07) 기간과 겹쳐 오염 가능성이 있다는 걸 항상 전제로 깐다.

## 13. 남은 불확실성

1. **파일 총 행수 불일치**: 메타데이터 206,022 vs 본 세션 파싱 226,759 — 원인 미상, 정식 CSV 파서로 재검증 필요.
2. **반경 450~500m 는 표본 3건 기반** — N≥20 재확정 전엔 provisional.
3. **odcloud/오픈API 대안(§2.3)** — 존재 가능성만 확인, 실제 사용 가능 여부 미검증(파일 다운로드로 충분하면 조사 불필요할 수도 있음).
4. **의왕 더샵캐슬 정확 좌표** — 본 세션은 인근 정류장 이름으로 간접 확인했을 뿐, 아파트 자체의 정확한 위경도로 500m 이내 검증까지는 못 했다(zigbang/kbland 스크래핑 차단·JS 렌더링으로 좌표 취득 실패). 구현 착수 시 `apartments` 테이블에서 직접 조회해 정밀 검증.
5. **02:00 naver-units-night 작업의 현재 잔존 여부** — `naver-units.mjs`(세션233 삭제)를 가리키던 예약 작업이 지금도 등록돼 있는지, 아니면 이미 정리됐는지 미확인(register-*.ps1 주석에서만 언급, 실제 `Get-ScheduledTask` 확인은 이 세션 범위 밖).
6. **§1 의 "서비스별 정책 차이" 가설도 확정이 아니다** — TAGO 쪽이 왜 간헐적으로 실패하는지 근본 원인은 여전히 모른다. B안이 그 원인을 몰라도 유효하다는 게 이 설계의 강점이지만, "왜"에 대한 답은 이 문서로 닫히지 않는다.
