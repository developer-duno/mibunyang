# 운영 데이터를 바꾸는 실행은 **전이표로 승인**받고, 안전장치는 **미리보기 뒤에** 발동한다

## 한 줄

**"규칙"을 승인받은 것과 "결과"를 승인받은 것은 다르다.** 사장님은 판정 규칙(applyhome 존중 · KOSIS 0 → 0)을
정했지만, 그 규칙이 **몇 곳을 어떻게 바꾸는지**(값>0 → 0 285곳, 손님 목록 −9.5%)는 본 적이 없었다. 규칙 승인만
믿고 돌리면 "승인받았다"는 말이 거짓이 된다. 그리고 실측 없이 정한 차단기 임계(10%)는 **첫 실행에서 반드시**
걸린다 — 첫 회차는 옛 값을 정리하는 일회성 대량 변경이기 때문이다.

> 사건·이력 (세션568 — 미분양 출처 칸 수리: 규칙 3가지를 승인받고 코드·시험·검사관 2회를 통과했는데, 운영 DB
> 첫 dry-run 에서 차단기(10%)가 13.7% 로 발동. 게다가 차단기가 `--impact-out` **앞**에 있어 승인용 미리보기가
> 아예 안 나왔고, 예외를 던져 이미 쓴 regions 뒤에서 멈추는 부분 반영 구조였다. 맹점 검사관(Opus)이 전이표를
> 직접 재현해 잡았다) → 세션 메모 `session_2026-09-24_session568_alert_schools_unsold_source.md`

## 규칙

### 1. 반영 전 **전이표**를 만들어 그것으로 승인받는다

전이표 = "지금 값 → 새 값" 조합별 개수 + 손님 화면에 닿는 수(기본 목록 증감·점수 등급이 바뀌는 수) + 대표 명단.
`--dry-run --impact-out=<파일>` 이 그 재료다. 규칙 이름(write·write_zero…)이 아니라 **값의 변화**로 센다:
값→다른 값 / 값>0 → 0 / 빈칸 → 값 / 값 → 빈칸 / 변화 없음.
분류 칸(`presale_type` 등)을 비우면 **화면 분류가 바뀌는 행**(예: `isLeaseUnit` 전/후 — 임대가 분양으로 나타나는 수)을 따로 센다 — 세션578: 214곳 중 39곳이 남의 링크에서 온 임대 유형이라 비우면 21곳이 목록에 새로 나타날 뻔 → `--keep-lease-type` 으로 2단계 반영.
**수집기가 매칭해서 덮어쓰는 칸**(링크·번호·분양 칸·출처처럼 "빈칸만 채움"이 아니라 매 회차 다시 정하는 값 — 쓰기 방식은 코드로 먼저 가른다)을 손으로 고치면 전이표에 **"반영 뒤 세 시점" 열**을 넣는다: ① 즉시(VIEW 폴백 `latest_*` 가 다음 후보를 올리는가 — 세션578 함정 10) ② 다음 굽기(정적 JSON) ③ **다음 수집 회차**(그 수집기의 판정 함수 — 예 `naver-presale.mjs` `matchPresaleToApt` — 를 탐침 캐시 재료로 불러 흉내, 네트워크 0; 캐시의 저장 시각·범위를 함께 적는다 — "32→1" 은 257건 캐시 안의 결과다). 탐침 캐시가 없는 수집기(KOSIS·학교·좌표)는 dry-run(호출 수를 지시서에) 또는 "확인 불가 + 확인 예정일" 로 적는다. 되채워지기를 **원하는** 정리(파생표 삭제 → 재수집)는 이 열이 아니라 `purge-to-recollect-timing` 의 시각 창이 잣대다. 세션579: 89곳을 반영한 **뒤에야** 흉내 → 끊은 79개 중 32개가 월요일에 다시 붙는 것을 발견(게이트 PR #650 으로 막음). 방식 참고 = 로컬 `.omc/artifacts/session579/simulate_relink_wt.mjs`(깃 밖 — 레포 안 정본은 BACKLOG A-13 후속) · 짝 = 메모리 [[manual-fix-must-survive-next-run]].
**묶음 열쇠의 재료 칸**(`name`·`region`·`gu`·`lat`·`lng`·`presale_type`)을 여러 행에서 바꾸는 반영은 `apartments.complex_key` 를 바꾼다(세션589) — 전이표에 `assign-complex-keys.mjs` 미리보기의 "바뀜" 명단을 넣고, 30행·10% 를 넘으면 매일 배치가 차단기에 걸려 새 행 채움까지 멈추므로 반영 직후 승인한 계획 파일(`--apply-from`)로 열쇠를 같이 옮긴다.

### 2. 차단기·검증은 **미리보기 출력 뒤, DB 쓰기 전**에

```
조회 → 계획(순수 함수) → 미리보기 저장(--impact-out 항상) → 차단기 판정 → (통과) 쓰기
```

- dry-run 에서 차단기 발동 = **경고 + 계획 저장 + exit 0**(미리보기라 아무것도 안 쓴다).
- 실제 실행에서 발동 = **아무것도 쓰지 않고**(앞 단계 표 포함) 실패 기록 + exit 1. 앞 단계를 이미 썼다면 그 순서가 틀린 것이다.
- 우회는 비율 완화가 아니라 **승인한 숫자와 정확히 같을 때만**(`--expect-zero=<N>`) — 전이표의 숫자가 곧 승인이다(승인한 것이 숫자 하나일 때. 행마다 값이 다른 **명단**이면 아래 계획 파일 대조로).
- 임계는 **첫 실행 비율을 실측한 뒤** 정한다(첫 회차는 예외적으로 크다 — 그 값은 우회 인자로 통과시키고, 임계는 평시용).
- 승인한 것이 **명단**(행마다 값이 다른 반영)이면 숫자 일치로도 부족하다 — 개수는 같고 내용이 다른 반영이 통과한다. 승인한 계획 파일과 **id·이전 값·새 값까지** 맞대고(`--apply-from=<계획 파일>`), 쓸 때도 이전 값이 그대로인 행만 고친다. 그 파일을 덮어쓸 수 있는 인자(`--out`)와는 같이 못 주게 한다(같은 경로면 덮어쓴 뒤 자기와 맞댄다 — 세션588 `assign-complex-keys.mjs`).
- 쓰기 도구의 인자는 **허용 목록**으로 읽는다(모르는 인자는 던진다). `recordCollectorRun` 은 실행 인자에 `--dry-run` 이 있으면 기록을 건너뛴다(`_shared.mjs`) — 자체 미리보기 스위치를 가진 도구에 습관대로 `--dry-run` 을 붙이면 **쓰고도 기록 0행**이 된다. 실패 기록도 "쓰려던 실행"의 모든 길(안전장치·예외·일부 행 실패)에서 남는지 인자 조합별로 본다.

### 3. 되돌릴 사본을 먼저 뜬다

1,000행 넘게 덮어쓰기 전에 `(id, 바뀌는 칸들, updated_at)` 을 파일로 뜨고, 역방향 계획(expect = 새 값 → set = 옛 값)을
`backfill-*.mjs --plan=` 꼴로 돌릴 수 있게 둔다. "impact 파일이 있으니 되돌릴 수 있다"는 착각이다 — impact 는
**의도**이지 실제 DB 상태가 아니다.
적용 = `backfill-unsold-source.mjs --plan=<계획.json>`(행마다 expect 대조 뒤 set, `--apply` 없으면 dry-run). 출처를 applyhome 으로 set 할 땐 `unsold_as_of`(공고일)도 같이 넣는다(세션569 C6).

### 4. "조용히 버리던 것"을 고칠 때는 로그가 아니라 **기록**으로

무음 `continue` 를 로그 한 줄로 바꾸면 로컬 러너 기록에만 남아 아무도 못 본다(#595). 최소 `collector_runs` 의
skip/warn 수치나 감시 항목으로 올린다 — 로그는 사람이 읽으러 가야만 보이는 자리다.
적용 = `REGION_UNRESOLVED` 마커(`collector_runs.error_message`, status 는 그대로) + monitor ⑪ `checkRegionUnresolved`(세션569). skip 칸은 감시 ②⑤가 "원천 정상 응답"으로 읽어 경보를 끄므로 쓰지 않았다.

### 5. 수집기의 넣기·건너뛰기 규칙을 바꾸는 결정은 **여쭙기 전에** "켜는 첫 회차에 몇 건이 움직이나"를 센다

수집기는 매 회차 같은 후보를 다시 본다 — 건너뛰던 조건을 풀면 **그동안 밀린 후보가 첫 회차에 한꺼번에** 들어온다.
직전 회차 로그(`gh run view <id> --log` · 로컬 러너 로그)에서 그 조건으로 건너뛴 줄을 세어 질문에 함께 적는다.
사례(세션586): seed 가 "네이버 행이 이미 있다"로 건너뛰던 공고를 넣기로 정한 **뒤에야** 9/28 로그를 세어 67건(59단지)
일괄 삽입임을 알았고, 같은 날 구조 결정을 두 번 뒤집었다.
**운영 DB 일회성 반영(명단을 스크립트로 판정해 기존 도구에 넘기는 경우 · 손으로 짠 삭제 스크립트 포함)은 반영 전에 그 명단을 검사관이 본다**
(인원 = 전역 model-selection 1-1 ② — 적대 Opus + 맹점 Opus). 사장님 승인은 "무엇이 바뀌는지"의 승인이지 명단 판정이 맞다는 검증이 아니다
(세션586: 34곳 끊기를 승인 직후 반영, 검사는 사후 — 34곳은 맞았지만 "보류" 5곳이 전부 끊을 대상이었고, 손 삭제 3행 중 1행의 근거 문장이 틀렸다).
이 파일은 수집기·정리 스크립트를 읽을 때만 불려온다 — 루트 CLAUDE.md "운영 데이터를 바꾸는 실행" 줄이 상시 통로다.

## 안티 패턴
