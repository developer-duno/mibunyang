# 외부 파일 자료의 중복 등재 — 총량 대조 의무 + 상한은 dedup 뒤에

## 한 줄

**"몇 건인가"를 세는 외부 파일은 같은 실체를 여러 행에 나눠 담는 경우가 흔하다.** 두 출처가 어긋날 때
"갱신 시점 차이"로 넘기지 말고 **총량을 맞대 정의 차이를 먼저 가른다**. 그리고 그런 자료에 상한(cap)을
걸 땐 **중복 제거를 먼저, 자르기를 나중에** 한다 — 순서를 바꾸면 중복이 촘촘한 곳일수록 조용히 손해를 본다.

## 사고 박제 (세션 498, 2026-08-07)

PR #337(버스 TAGO → data.go.kr 정적 파일 전환)이 남긴 위험 항목:

> ±1 교차검증 48% — 두 독립 소스 간 자연스러운 스냅샷 차이로 해석했으나, 확정은 아니다.

사장님 지시로 규명에 들어갔다. **"시점 차이" 설명은 검증된 적이 없는 가설이었다.**

### 실측으로 가른 결과 — 시점이 아니라 세는 기준

```
국토부 전국 파일 서울분 : 16,980 행
서울시 TOPIS 공식      : 11,231 건      → 국가 파일이 51% 많음
서울분 고유 좌표       : 16,980 (= 총 행수, 모든 행이 서로 다른 좌표)
서울분 고유 이름       :  9,057
이름 등장 횟수         : 1회 3,841 / 2회 3,914(최다) / 3회 369 / 4회 712 / 5회+ 221
서울분 정보수집일      : 전부 2025-10 한 달   ← 시점이 섞여 있지도 않았다
```

9개월 사이 정류장이 51% 늘 수는 없다 → **시점 가설 기각**. "같은 이름 2회"가 최다이고 모든 행의
좌표가 다르다 → **정류장 기둥 하나를 방향별(상·하행)·지자체 체계별로 나눠 담은 구조**.
두 자료는 같은 실체를 다르게 센 것이지 어느 쪽이 틀린 게 아니다.

### 규명 중 드러난 진짜 결함 — 상한을 dedup 앞에 걸었다

중복 구조를 알고 나니 `matchNearbyBusStops` 가 **dedup 전에 15개로 자르는** 게 문제로 드러났다.
중복이 촘촘한 도심일수록 15칸이 같은 정류장의 중복 행으로 채워진다. 전 단지 2,635곳 재계산:

| | 옛 순서 (cap 先) | 새 순서 (dedup 先) |
|---|---|---|
| 만점 버킷 | **0곳** (아무도 만점 불가) | 795곳 |
| 실제보다 적게 센 단지 | **1,449곳 (55%)** | — |
| 평균 손실 | **2.54개** (= 원점수 5.08점) | — |

**지역 편향**: 대구 -10.05 · 서울 -9.47 · 부산 -8.60 vs 제주 -0.40 · 대전 -0.60.
**도시일수록 손해** — 중복 등재 밀도가 도심에서 높기 때문. 균일한 오차가 아니라 **체계적 편향**이다.

### 잣대 자체가 무효였다 (같은 문서 안의 모순)

옛 순서의 근거는 "옛 TAGO DB 값과의 재현율 44%→64%"였다. 그런데 **그 옛 값이 서울에서 통째로
거짓이었다는 게 그 PR 의 출발점**이다. 한 문서가 한쪽에선 "그 일치율은 틀린 잣대로 옳은 답을 재고
있었다"고 결론짓고, 다른 쪽에선 그 일치율로 알고리즘 순서를 정했다.

## 재발 방지 (3중)

### 1. 두 출처가 어긋나면 **총량부터 맞댄다** (시점 가설 단정 금지)

"갱신 시점이 달라서"는 **가장 흔한 미검증 변명**이다. 단정 전 다음을 실측:

```bash
# (a) 총량 비교 — 같은 범위(시도/지역)로 잘라서
#     ±5% 안 → 세는 기준 같음(시점·좌표 차이 의심)
#     수십 % 차이 → 정의 차이 확정 (시점으로는 설명 불가)
# (b) 고유 키 수 vs 총 행수
#     고유 좌표 == 총 행수인데 고유 이름은 훨씬 적다 → 한 실체를 여러 행에 나눠 담음
# (c) 같은 이름 등장 횟수 분포
#     "2회"가 최다 → 방향별(상·하행) 분리의 전형
# (d) 자료의 기준일 컬럼 분포
#     한 달에 몰려 있으면 "시점이 섞여서" 가설은 그 자리에서 죽는다
```

(d)를 먼저 보면 1분 만에 끝나는 경우가 많다. **가설을 세웠으면 그 가설을 죽일 수 있는 관측부터** 한다.

### 2. 중복 등재 자료에 상한을 걸 땐 **dedup 先 → cap 後**

```js
// 빨강 — 중복이 상한 칸을 먹는다 (도심일수록 손해)
candidates.sort(byDistance).slice(0, CAP).map(toItem)   // 뒤에서 dedup 해봐야 이미 늦음

// 초록 — 고유 기준으로 상한을 채운다
const seen = new Set(), out = [];
for (const s of candidates.sort(byDistance)) {
  if (seen.has(s.key)) continue;
  seen.add(s.key); out.push(s);
  if (out.length >= UNIQUE_CAP) break;
}
```

상한의 의미를 **"원시 행 N개"가 아니라 "고유 실체 N개"** 로 못 박는다. 그래야 자료 출처의 중복
등재 방식이 바뀌어도 값의 뜻이 흔들리지 않는다.

### 3. 수집 상한과 만점 기준은 **같은 값 + 기계 가드**

수집 상한이 만점 기준보다 **낮으면 어떤 대상도 만점을 못 받고**(옛 상태: 상한 15 → dedup 후 항상
15 미만 → 만점 버킷 0곳), **높으면** 초과분을 저장만 하고 점수엔 못 쓴다. 두 상수가 다른 파일에
살면 반드시 어긋나므로 테스트로 묶는다 — 값을 테스트에 적지 말고 **소스에서 읽어 비교**한다.

```js
const CAP = Number(collectorSrc.match(/^const BUS_UNIQUE_CAP = (\d+);$/m)?.[1]);
const FULL = Number(tiersSrc.match(/^export const FULL_BUS_ROUTES = (\d+);$/m)?.[1]);
expect(Number.isFinite(CAP)).toBe(true);   // 정규식이 죽으면 아래 비교가 무의미해진다
expect(CAP).toBe(FULL);
```

줄 시작·끝(`^`/`$`)을 고정해 주석줄에 걸리지 않게 한다 — [[guards-must-be-mutation-tested]] §"소스 grep 가드".

## 상한을 올릴 때 — 만점 비율로 정한다

상한을 고치면 **만점 몰림**이 새 문제가 된다(세션488 이 지적한 "만점 몰림 → 변별력 소멸"의 반대
방향 재발). 상한 없이 실제 분포를 먼저 재고, **만점 비율**로 기준을 고른다.

| 실측 (반경 500m 고유 정류장, 2,635곳) | 값 |
|---|---|
| 중앙값 / 평균 | 10 / 11.24 |
| p75 / p90 / p95 / p99 / 최대 | 16 / 20 / 24 / 30 / 49 |

| 만점 기준 | 만점 비율 | 판정 |
|---|---|---|
| 15 | 30.2% | 세 곳 중 한 곳이 동점 — 비교 엔진이 비교를 못 함 |
| **20** | **13.9%** | **채택** (상위 10%대만 만점) |
| 25 | 4.4% | 사실상 도달 불가 |

## 안티 패턴

- ❌ "두 출처가 다른 건 갱신 시점 차이" — **총량·기준일 분포를 보기 전엔 가설일 뿐**. 이번엔 기준일이 한 달에 몰려 있어 그 자리에서 죽었다
- ❌ "일치율이 낮지만 핵심 명제와 무관하니 넘어간다" — 핵심 명제(있다/없다)와 무관해도 **그 수치가 점수에 들어가면** 별개 문제다. "무관"은 명제에 대해서지 영향에 대해서가 아니다
- ❌ "재현율이 높은 쪽이 정답" — **재현 대상이 거짓이면 재현율은 거짓을 잘 흉내낸 정도**다. 잣대의 정당성을 먼저 확인
- ❌ 평균 오차만 보고 "허용 범위" 판정 — 지역·구간별로 쪼개야 **체계적 편향**이 보인다(전체 평균 2.54개 뒤에 대구 -10.05점이 숨어 있었다)
- ❌ 상한 상수를 테스트에 숫자로 적기 — 상수만 바꿔도 테스트가 따라와 "어긋난 채 초록불"
