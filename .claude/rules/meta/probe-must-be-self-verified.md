# 측정 도구부터 의심하라 — 탐침에 **양성 대조군**을 붙인다

## 한 줄

**"실측했다"는 그 측정이 옳았다는 뜻이 아니다.** 조회 한 줄, 함수 호출 한 번이 틀리면 결론이 통째로 뒤집히는데, 결과가 그럴듯해 보이면 아무도 다시 보지 않는다. 원인은 매번 같았다 — **확인하지 않고 추측으로 썼다.**

## 규칙

1. **탐침에 양성 대조군을 먼저 붙인다** — 본 측정 전에 "답이 나와야 하는 입력"(예: 값이 이미 있는 단지 5곳)으로 같은 호출을 돌린다. 안 나오면 도구가 틀린 것이다.
2. **`Number(null)` 은 0 이다** — 빈칸을 셀 땐 `r[f] == null` 과 `r[f] != null && Number(r[f]) === 0` 을 가른다. 한 곳을 고쳤으면 같은 셈을 하는 다른 곳도 고쳤는지 확인.
3. **새 함수는 시그니처를 먼저 읽는다**(`grep -n "export function <이름>" -A 5 <파일>`) — 인자 순서·단위(m vs km)를 추측하지 않는다.
4. **조회가 `null` 을 돌려주면 에러를 의심** — Supabase 는 데이터가 없으면 `[]`, `null` 이면 실패. 탐침에는 항상 `.error` 를 찍는다.
   - 없는 컬럼명이 섞이면 `data` 는 null → "행 없음"으로 오독. 컬럼을 모르면 `select("*")` 로.
   - `select("*", { count: "exact", head: true })` 는 없는 표에도 error=none·count=null → "표 없음"은 실제 `select("*").limit(1)` 의 에러 코드(PGRST205)로만, 있는 표/없는 표 대조군을 같이 돌린다.
5. **날짜 문자열을 `new Date()` 에 넘기지 마라** — `new Date("202211-01")` 은 서기 202211년(에러도 NaN 도 아님). 정규식으로 형식을 강제하고 월 1~12 검사 + **월 단위 정수**로 비교. 이미 있는 `src/scoring/scorePrice.ts` `parseCompletionMonth` 를 먼저 찾는다. 분류가 한쪽으로 100% 나오면 그 자체가 의심 신호 — 실제 값 몇 개를 눈으로 찍어 본다.
6. **`.find(name === ...)` 로 단정하지 않는다** — 동명이 흔하다. 이름으로 찾을 땐 전부 세고, 필요하면 좌표까지 본다.
7. **오측정이 의심되면 결론이 아니라 도구를 먼저 재검한다** — 결과가 직전 실측과 모순되면 가설보다 탐침부터.
8. **단지 하나를 조사하면 그 행 전체의 상식을 한 번 본다** — 분양 번호가 자기 번호인지(`naver_presale_no` ↔ id)·지역이 맞는지·가격이 그 지역 상식인지.

## 적용 시점 (의무)

- DB 를 세어 **작업 대상을 정할 때** (이 수치로 PR 범위가 정해진다)
- **"0곳"·"없음"·"불가능"** 같은 부재 결론이 나왔을 때 — §1 양성 대조군 필수
- 남이 만든 함수를 처음 호출할 때 — §3
- 그 수치를 **커밋 메시지·코드 주석·문서에 박기 직전** — §2 다른 자리도 고쳤는지

## 안티 패턴

- ❌ "실측했으니 맞다" — 측정 도구가 틀리면 실측도 틀린다
- ❌ 부재 결론("0곳")을 대조군 없이 채택 — **실패가 조용해서** 아무도 안 본다
- ❌ 함정을 한 곳에서 피했다고 다 피한 줄 앎(세션537 5번)
- ❌ 결과가 모순되는데 가설부터 고침 — 도구를 먼저 본다
